# TRACKBACK 게임화 리디자인 설계서 v1

> 상태: 향후 TRACKBACK 조사 UX 및 게임화 개발의 기준 문서  
> 기록일: 2026-10-01  
> 적용 원칙: 기존 차량 고장 분석 구조를 유지하면서 Mission, Clue, Character, Repair, Re-drive, Reward 레이어를 단계적으로 구축한다.

## 1. 목표

기존의 차량 고장 원인 분석 구조를 버리지 않고, 플레이어가 다음 감정을 느끼게 만드는 것이 목표다.

- 고장이 났을 때 “무슨 일이지?”라는 궁금함
- 조사하면서 “아, 여기까지는 정상이고 여기서부터 이상하네”라는 발견감
- 가설을 시험하면서 “내 생각이 맞나?”라는 긴장감
- 정답 시 “내가 이 차를 고쳤다”는 성취감
- 다시 주행하면서 “진짜 정상화됐다”는 확인감

분위기는 **동물의숲의 느긋한 진행과 작은 행동 목표**, **치이카와의 아기자기함과 약간의 곤란함을 함께 해결하는 감정선**을 참고한다.

단, 외형/캐릭터/자산을 직접 복제하지 않고 TRACKBACK만의 **고양이 운전자 + 정비소 + 차량 검증** 세계관으로 만든다.

## 2. 전체 게임 루프

현재의

```text
주행
→ 고장
→ 조사
→ 정답
→ 끝
```

을 아래처럼 바꾼다.

```text
주행 미션
↓
고장 발생
↓
고양이 반응 / 사건 접수
↓
짧은 조사 미션 여러 개
↓
단서 수집
↓
가설
↓
시험
↓
결론 제출
↓
성공/실패 피드백
↓
수리
↓
재주행 검증
↓
보상
↓
다음 에피소드
```

핵심은 **조사 페이지 자체가 게임의 단계가 아니라, 미션을 해결하기 위한 도구**가 되는 것이다.

## 3. Episode 단위 구조

한 고장 사건을 하나의 Episode로 본다.

예:

```text
EPISODE 01
"힘이 안 나와!"
```

구조:

```text
Intro Drive
↓
Fault Event
↓
Mission 1: 현상 확인
↓
Mission 2: 관련 기능 찾기
↓
Mission 3: 신호 조사
↓
Mission 4: 정상 기준 확인
↓
Mission 5: 가설 시험
↓
Final Report
↓
Repair
↓
Re-drive
↓
Reward
```

초반 Episode는 안내가 많고, 뒤로 갈수록 안내를 줄인다.

## 4. 기존 Page 1~4의 역할 재정의

### Page 1 = 사건 보고서

현재 구조는 유지한다.

역할:

> “무슨 일이 발생했는지 이해하는 곳”

플레이어 목표:

```text
운전자가 무엇을 요청했는가?
↓
당시 차량 상태는 어땠는가?
↓
차량은 실제로 어떻게 반응했는가?
```

게임 레이어:

- 고양이 운전자 대화
- Mission 01 표시
- 필요한 부분만 은은하게 강조
- 확인 완료 시 작은 스탬프

예:

> **MISSION 01 · 사건 기록 확인**  
> 당시 입력과 차량 반응을 살펴보세요.

완료:

> `✓ 사건 상황 확인 완료`

## 5. Page 2 = 조사실

Page 2는 사실상 TRACKBACK의 핵심 플레이 공간이다.

기존 탭:

- 기능 흐름
- Signal Monitor
- Interface
- Requirement

는 유지한다.

하지만 플레이어는 이 네 개를 “순서대로 모두 거쳐야 하는 단계”로 인식하지 않게 한다.

대신 현재 Mission 하나를 보여준다.

예:

> **MISSION 02 · 어디서부터 달라졌을까?**  
> 차량 반응에 가까운 기능부터 살펴보세요.

각 도구의 의미:

```text
기능 흐름
= 어디를 조사할지 찾는 지도

Signal Monitor
= 실제 값과 상태를 확인하는 도구

Interface
= 기능 사이에서 값이 제대로 전달됐는지 확인하는 도구

Requirement
= 원래 어떻게 동작해야 하는지 기준을 찾는 매뉴얼
```

## 6. Mission 시스템

Mission은 길게 설명하지 않는다.

형식:

```text
현재 목표
짧은 한 문장

선택적 힌트
한 줄
```

예:

```text
MISSION 03
입력은 정상인데 출력부터 달라지는 기능이 있는지 확인하세요.

힌트
상태 → 입력 → 출력 순서로 보면 비교하기 쉽습니다.
```

Mission의 목적은 정답을 알려주는 것이 아니라, **현재 어떤 판단을 해야 하는지 알려주는 것**이다.

## 7. 고양이 운전자 역할

고양이 운전자는 기술 설명 담당이 아니라 **감정과 상황을 전달하는 캐릭터**다.

### NORMAL

- 운전 집중
- 즐거움
- 가벼운 미소

### FAULT

- 놀람
- 귀 내려감
- 눈 커짐
- 땀방울

### THINKING

- 턱 괴기
- 고개 갸웃

### INVESTIGATING

- 돋보기 들기
- 모니터 가까이 보기

### CLUE_FOUND

- 눈 반짝
- 손 들기
- “앗!”

### WRONG

- 시무룩
- 고민

### SOLVED

- 방방 뜀
- 박수

### REPAIRED

- 만족
- 운전석으로 다시 뛰어감

## 8. 엔지니어 고양이 역할

엔지니어 고양이는 두 역할만 가진다.

### 조사 안내

짧은 말만 한다.

예:

> “이 기능의 입력부터 확인해볼까요?”

> “값의 기준이 필요하면 요구사항을 찾아보세요.”

길게 강의하지 않는다.

### 수리 연출

정답 이후 등장.

- 렌치 돌리기
- 차량 아래 들어가기
- 노트 들고 체크
- 서로 끄덕이기
- 타이어/보닛 주변에서 작업

F1 피트크루처럼 빠르게 움직이되 전체 분위기는 귀엽고 느긋하게.

## 9. 단서 시스템

현재 Evidence 개념을 게임적으로 바꾼다.

### 관찰 단서

실제 신호/상태 확인

예: `GearState = DRIVE`

### 차이 단서

Expected/Actual 또는 경계 비교

예: `EDriveCommand Actual ≠ Expected`

### 기준 단서

Requirement에서 얻은 기준

예: `VALID + FORWARD 조건에서 torque limit 적용`

### 시험 단서

Page 3 실행 결과

예: `TC-... FAIL`

## 10. 단서 획득 연출

단서를 찾았을 때:

```text
🔎 단서 발견!
```

작은 효과음.

그리고 카드가 조사 노트로 이동.

예:

```text
CLUE #03

EDriveCommand

Actual 45 Nm
Expected 90 Nm

출력이 기대값과 다름
```

정상도 단서다.

```text
✓ 정상 확인

GearState
DRIVE

조건 만족
```

정상 단서도 범위를 좁히기 때문이다.

## 11. 조사 노트

왼쪽 sidebar의 Evidence를 발전시킨다.

조사 노트에는:

- 획득한 단서
- 저장한 기준
- 시험 결과
- 현재 가설

이 들어간다.

단순 숫자 `3개`보다 실제 작은 카드 목록을 보여주는 게 좋다.

각 단서는 클릭하면 원래 위치로 돌아갈 수 있다.

## 12. Signal Monitor의 게임 역할

Signal Monitor는 단순 그래프 viewer가 아니라:

> “어디까지 정상이고 어디서부터 이상한지 찾는 퍼즐”

로 정의한다.

화면 상단 질문:

> **입력은 정상인데 출력부터 달라지는 곳이 있나요?**

플레이어는:

```text
상태
↓
입력
↓
출력
```

을 비교한다.

의미 있는 차이를 찾으면 단서가 나온다.

중요:

- 아무 신호나 클릭했다고 단서 주지 않음
- 정상/이상 판단 근거가 있어야 단서
- Actual-only면 “판단 불가”도 유효한 관찰

## 13. Interface의 게임 역할

Interface는:

> “전달 중 값이 바뀌었는지 확인하는 도구”

로 명확히 한다.

질문:

> **Source가 보낸 값과 Destination이 받은 값이 같은가요?**

플레이어가 두 값을 비교.

결과:

```text
같음
→ 전달 경계 정상

다름
→ 인터페이스 의심
```

이 결과도 단서화.

## 14. Requirement의 게임 역할

Requirement는 문서창이 아니라:

> **정비 매뉴얼 / 기준 책**

으로 느껴지게 한다.

Mission 예:

> “이 값이 원래 어떻게 나와야 하는지 기준을 찾아보세요.”

플레이어가 Requirement를 확인하면:

```text
📘 기준 발견!
```

전문 정보는 유지하되:

1. 쉬운 설명
2. 기술 표현

순으로 보여준다.

예:

```text
쉬운 설명
정상 방향 요청일 때 출력 토크는 제한값 안이어야 합니다.

Technical
IF Validity == VALID
AND Direction == FORWARD
THEN ...
```

## 15. Page 3 = 시험실

Page 3은 가장 “시뮬레이션 검증”스럽게 만든다.

시각적 흐름:

```text
가설
↓
조건
↓
입력
↓
관찰 출력
↓
시험 실행
↓
결과
```

게임적 연출:

```text
3
2
1
TEST!
```

그 뒤 차량/모델 반응.

고양이도 모니터 바라봄.

결과:

```text
시험 판정: FAIL

하지만:
"이 시험은 해당 동작이 기대 기준을 만족하지 않았음을 의미합니다."
```

즉 FAIL=Root Cause 정답으로 오해하지 않게 한다.

## 16. 가설 시스템

가설은 단순:

```text
eDrive
Logic Error
```

가 아니라:

```text
의심 위치
eDrive

예상
정상 입력 조건에서도 출력 토크가 기대값보다 작을 것이다.
```

정도로 구성한다.

플레이어는 이 예측을 시험한다.

## 17. Page 4 = 사건 보고서 제출

UI는 정비소 문서/조사 보고서 느낌.

구성:

```text
사건 보고서

원인 위치
문제 유형

선택한 단서
☑ 단서 02
☑ 단서 04
☑ 시험 01

[보고서 제출]
```

제출 시 도장.

성공:

```text
CASE SOLVED
```

실패:

```text
RECHECK
```

다만 실패도 공격적으로 표현하지 않는다.

## 18. 성공 연출

성공 시 흐름:

```text
보고서 승인
↓
고양이 눈 반짝
↓
엔지니어 고양이 호출
↓
수리 컷신
↓
REPAIRED!
↓
운전자 고양이 감사
↓
재주행 준비
```

대사 예:

> “찾았다! 여기였구나!”

> “고마워! 이번엔 다시 달려볼게!”

## 19. 수리 컷신

처음엔 복잡한 3D 애니메이션 필요 없음.

2D/overlay 연출로 충분.

예:

- 엔지니어 고양이 3마리 등장
- wrench icon
- 작은 spark
- 너트 튀는 효과
- 차량 흔들림
- progress 0→100

```text
REPAIRING...
■■■■■■■■□□
```

완료:

```text
✓ REPAIRED
```

## 20. 재주행 검증

수리 후 같은 조건에서 다시 주행.

이게 매우 중요.

```text
BEFORE
목표 시간 실패
가속 저하

AFTER
정상 가속
목표 시간 달성
```

플레이어가 직접:

> “진짜 고쳐졌구나”

를 체감.

이게 곧 Regression / Verification의 게임적 표현이 된다.

## 21. 보상 시스템

처음엔 간단하게.

가칭:

```text
냥코인
```

획득:

```text
사건 해결 +30
재주행 성공 +20
적절한 근거 선택 +10
```

하지만 감점은 최소화.

힐링 분위기니까:

- 틀려도 돈 차감 없음
- 시간 제한 없음
- Game Over 없음

## 22. 코인 사용처

처음엔 실제 구매 시스템 없어도 됨.

추후:

- 차량 스티커
- 고양이 모자
- 정비소 소품
- 차량 색
- 조사 노트 스킨
- 배경 장식

이 정도.

즉 성능 Pay-to-win 요소는 넣지 않는다.

## 23. 스티커 / 수집 요소

TRACKBACK하고 아주 잘 맞음.

사건 해결할 때마다 스티커 지급.

예:

```text
🔧 FIRST REPAIR
🔎 SIGNAL SLEUTH
📘 REQUIREMENT READER
🏁 BACK ON TRACK
```

노트나 차고 벽에 붙임.

동물의숲의 수집/꾸미기 감각과 잘 맞는 부분.

## 24. BGM 구조

한 곡 계속 틀지 말고 상태별로 바꾼다.

```text
Drive
→ 경쾌

Fault
→ 잠깐 끊기거나 작은 당황 효과

Investigation
→ 잔잔하고 집중 가능한 음악

Clue found
→ 짧은 밝은 효과음

Test
→ 약간 긴장

Solved
→ 밝은 jingle

Repair
→ 통통 튀는 리듬

Re-drive
→ 원래 Drive BGM 복귀
```

힐링 게임이라 과한 긴장 음악은 피한다.

## 25. 효과음

작은 인터랙션 피드백 위주.

- 버튼: 종이/목재 느낌
- clue: `띵`
- requirement: 책장 넘김
- stamp: `꾹`
- repair: `딱딱 / 뚝딱`
- success: 짧은 jingle
- coin: 가벼운 동전음

## 26. UI 정보량 원칙

매 화면 기본 상태에서는:

```text
현재 Mission
+
현재 판단에 필요한 핵심 정보
+
선택 행동
```

만 보인다.

나머지는:

- hover
- tooltip
- 펼치기
- 자세히
- 기술 정보

로 숨긴다.

즉:

> **게임 정보 먼저, 공학 정보는 두 번째 레이어**

## 27. 초보자/어린이 기준

첫 Episode:

- 고양이 대화 많음
- Mission 구체적
- UI 강조
- 기술 용어 툴팁 많음

Episode 2:

- 안내 절반

Episode 3:

- 목표만 제시

Episode 4 이후:

- 거의 자유 조사

이렇게 학습 곡선을 만든다.

## 28. 앞으로의 구현 순서

### Phase A — 현재 조사 의미 구조 안정화

- signal evidence
- interface 양단 비교
- hypothesis/test target
- FAIL 의미
- evidence lifecycle

### Phase B — Mission/Clue layer

- 현재 목표
- 단서 발견
- 조사 노트
- 고양이 짧은 대사

### Phase C — Character reactions

- normal
- fault
- thinking
- clue
- solved

### Phase D — Repair/Re-drive loop

- 수리 컷신
- 정상화
- 재주행

### Phase E — Reward / cozy polish

- 냥코인
- 스티커
- BGM
- 효과음
- 장식

TRACKBACK은 최종적으로:

> **“고장 난 고양이 운전자의 차를 함께 조사하고, 실제 차량 검증 방식으로 원인을 찾고, 수리해서 다시 달리게 해주는 아기자기한 자동차 검증 어드벤처”**

정도로 잡으면 방향이 꽤 선명해진다.
