통합 게임 기획 및 개발지시서 — Version 3.0
개발 대상: 기존 레이싱·고장 추리·차량 아키텍처 프로젝트
게임 장르: 코지 정비소 + 차량 로직 퍼즐 + 검증 시뮬레이션 + 테스트 드라이브
핵심 학습: 차량 도메인, 시스템 구조, 요구사항, 제어 로직, 소프트웨어 검증
첫 구현 범위: 레이싱 오프닝, 정비소, READY 제어 퍼즐, 테스트, 기본 보상
장기 목표: 다양한 차량 기능과 검증 수준을 지원하는 재사용 가능한 교육 게임
사고로 엉망이 된 귀여운 프로토타입 자동차를 정비소에서 복구하면서, 차량 제어 기능을 직접 만들고 다양한 조건에서 검증한 뒤 테스트 트랙에서 성능을 확인하는 게임.
본 프로젝트는 자동차를 소재로 한 단순 퍼즐게임도, 자동차 시스템을 암기하는 교육 콘텐츠도 아니다.
플레이어는 자동차가 어떤 원리로 작동하는지 관찰하고, 제어 로직을 구성하고, 검증을 통해 제대로 작동하는지 확인한다.
이 과정에서 차량 도메인 지식과 실제 차량 SW 개발·검증의 사고방식을 학습한다.
검증 기업에서 수행하는 프로젝트라는 맥락을 고려하여 다음 과정을 핵심 경험으로 만든다.
요구사항 이해 → 로직 구성 → 테스트 조건 설계 → 시뮬레이션 → 판정 → 결과 분석 → 수정 및 재검증
플레이어가 반드시 개발자와 검증자의 역할을 구분해서 이해하도록 한다.
첫째, 자동차 도메인을 몰라도 게임을 시작할 수 있어야 한다.
둘째, 미션을 완료한 플레이어가 해당 차량 기능의 동작 원리를 설명할 수 있어야 한다.
셋째, 검증 과정이 부수적인 버튼이 아니라 재미있는 플레이의 일부여야 한다.
넷째, 직접 만든 로직이 차량 상태와 조작 결과에 영향을 주어야 한다.
다섯째, 귀엽고 완성도 높은 상용 인디게임 수준의 플레이 경험을 지향한다.
여섯째, 기술적 결과물은 자동차 SW 검증 직무 포트폴리오에서 설명 가능해야 한다.
본 설계는 다음 범주의 연구와 기술 자료를 참고한다.
1. 인지부하와 단계적 학습
2. 게임 기반 학습 및 게이미피케이션
3. 게임의 즐거움과 자기결정성이론
4. 인출 연습 및 학습 전이
5. UI의 점진적 정보 공개
6. 게임 접근성과 난도 조절
7. 자동차 SW 검증 표준
8. 차량 SW 가상 검증 및 테스트 재사용
9. 기능안전 및 요구사항 기반 개발
10. 게임 개발의 메커니즘·동역학·감성 경험
이러한 연구는 설계 방향의 근거이며, 본 게임의 교육 효과와 상품성을 보증하지 않는다.
처음부터 복잡한 자동차 아키텍처와 고장 로그를 제시하지 않는다.
플레이어가 현재 해결할 문제와 직접 관련된 입력, 출력, 조건만 보여준다.
새로운 개념은 기존에 학습한 로직 위에 하나씩 추가한다.
설계 규칙
- 한 미션에서 새로 학습할 핵심 개념은 1~2개를 목표로 한다.
- 필요한 로직 블록만 먼저 제공한다.
- 고급 정보는 선택적으로 확인한다.
- 처음부터 모든 ECU 및 인터페이스를 표시하지 않는다.
- 학습 전 고장 추리를 요구하지 않는다.
플레이어가 직접 선택하고 실험할 수 있어야 한다.
이를 위해 다음 요소를 도입한다.
- 자유로운 블록 연결
- 입력값 직접 조작
- 여러 가능한 로직 구성
- 실패 후 수정
- 재시험
- 차량 반응의 실제 변화
- 원하는 기능의 재방문 및 개선
단일 정답 그림을 맞히는 방식보다는 기능 요구사항을 만족하는 방식이 적절하다.
각 미션은 플레이어가 이해할 수 있는 한 문장으로 목표를 제시한다.
예시:
"브레이크를 밟고 시동 버튼을 눌렀을 때 자동차가 주행 준비 상태가 되도록 만드세요."
플레이어가 입력을 바꾸면 출력과 계기판이 즉각적으로 반응해야 한다.
검증에 실패했을 때는 실패한 테스트, 예상 결과, 실제 결과 및 관련 로직을 보여준다.
학습 활동이 실제 게임의 성취와 연결되어야 한다.
예를 들어 토크 제한 로직을 완성하면 단순히 별을 획득하는 것이 아니라 실제 테스트 트랙에서 차량 반응이 변하도록 한다.
게임 진행과 학습을 별도의 경험으로 분리하지 않는다.
플레이어는 작고 엉뚱한 자동차 개발소의 신입 정비 엔지니어다.
개발소에서는 귀엽고 조금 불안정한 프로토타입 EV를 시험하고 있다.
어느 날 테스트 트랙에서 주행 중 예상치 못한 사건이 발생한다.
차량이 범퍼카처럼 튀어 오르고, 범퍼와 장식물이 만화적으로 분리되며 정비소로 돌아온다.
이 사건으로 차량은 전반적인 점검과 제어 기능의 복구가 필요한 상태가 된다.
플레이어는 기능을 하나씩 정상화하고 테스트하여 자동차를 다시 완성한다.
코믹한 사고 장면 자체는 실제 자동차 고장 원리를 설명하는 장면이 아니다.
차량 외관의 물리적 파손은 정비소 캐릭터가 별도로 처리한다.
플레이어가 복구하는 것은 프로토타입의 제어 프로그램 및 시스템 동작이다.
따라서 SW 로직을 연결했기 때문에 실제 파손된 자동차 부품이 물리적으로 복원되었다는 잘못된 설명을 제공하지 않는다.
게임 속 복구 대상은 다음 두 종류로 구분한다.
외관·기계적 복구
연출과 스토리의 영역.
차량 제어 기능 복구
플레이어가 직접 수행하는 퍼즐 및 검증 영역.
목표는 아기자기하고 따뜻한 코지 게임이다.
- 말랑한 형태의 차량
- 파스텔 색상
- 부드러운 조명
- 장난감 같은 정비소
- 작고 귀여운 캐릭터
- 짧은 대사
- 과장된 코믹 애니메이션
- 작은 부품들이 통통 튀는 연출
- 전원·모터·계기판의 경쾌한 효과음
다만 실제 기존 게임의 캐릭터, 로고, 고유한 UI 배치, 아트 에셋을 복제하지 않는다.
독립된 미술 스타일과 세계관을 구축한다.
정비소에 소수의 캐릭터를 배치할 수 있다.
정비 도우미
자동차 기능의 원리를 설명하고 힌트를 제공한다.
테스트 담당 캐릭터
정상 조건만 통과하면 끝이 아니라 다양한 조건을 확인해야 한다고 알려준다.
차량 캐릭터
상태에 따라 표정과 반응이 변화한다.
캐릭터는 학습을 돕는 보조 역할이며 긴 대화가 필수는 아니다.
처음 버전에서는 캐릭터 수를 늘리지 않는다.
테스트 드라이브 → 문제 발생 → 정비소 → 기능 로직 구성 → 검증 → 기능 복구 → 테스트 드라이브 → 다음 기능
이 흐름을 모든 차량 도메인에 적용할 수 있도록 한다.
다만 모든 미션에서 반드시 새로운 사고가 발생할 필요는 없다.
일부 미션은 신규 기능 개발, 성능 개선 또는 검증 강화의 형태로 진행할 수 있다.
플레이어가 실제로 반복하는 행동은 다음과 같다.
1. 입력 조작
2. 블록 조립
3. 실행
4. 결과 관찰
5. 테스트
6. 수정
이 루프 자체가 즐거워야 한다.
시각적 효과는 테스트 실행 후에만 나타나는 것이 아니라, 블록을 연결하거나 신호를 변경할 때도 적절하게 제공한다.
미션을 완료하면 차량 기능이 활성화된다.
여러 기능을 완료하면 차량의 새로운 동작이 가능해진다.
기능을 조합하면 테스트 트랙에서 더 다양한 동작을 경험한다.
차량 시스템 지도를 점차 완성한다.
구동, 배터리, 충전, 제동, 열관리 등 새로운 기능을 학습한다.
이후 복수 기능 간 통신과 타이밍 문제를 검증한다.
후반에는 학습했던 로직을 응용해 이상 원인을 좁히는 챌린지를 수행한다.
기존 레이싱 파트는 폐기하지 않는다.
게임의 진입 경험, 성취 보상, 기능 실험 공간으로 활용한다.
오프닝에서는 조작 가능한 짧은 주행 구간을 제공한다.
플레이어는 차량을 이동시키고 코너를 돌며 기본 조작을 체험한다.
이후 스크립트로 제어되는 코믹한 사고 연출을 보여준다.
사용자의 조작 미숙을 고장 원인으로 강제하지 않는다.
오프닝이 길어지지 않도록 한다.
차량 기능을 완성하면 테스트 트랙에서 실제 영향을 확인한다.
예시:
- READY 완성: 차량 구동 준비 상태 표시
- 가속 로직 완성: 페달 입력에 따라 가속
- 토크 제한 완성: 특정 조건에서 가속 성능 제한
- 제동 로직 완성: 감속 기능 활성화
- 회생제동 완성: 감속 시 에너지 흐름 변화
단, READY 하나만 완성한 상태에서는 실제 가속·제동 제어를 새롭게 구현한 것으로 간주하지 않는다.
기존 주행 모델을 사용하는 경우에도 해당 로직과 실제로 연결된 기능 범위를 명확히 한다.
차량 조작 능력이 부족하더라도 로직 검증 학습을 완료할 수 있어야 한다.
레이싱은 보상 및 실험 공간으로 활용한다.
기술 학습의 필수 성공 조건을 주행 기록이나 랩타임에 두지 않는다.
주행 지원 옵션을 제공할 수 있다.
- 조향 보조
- 주행 속도 조절
- 자동 주행 시연
- 반복 재시작
- 레이싱 구간 건너뛰기
기존의 "로직을 만들고 테스트 버튼을 누르는 게임"에서 한 단계 발전시킨다.
플레이어가 무엇을 검증해야 하는지도 판단하는 게임으로 만든다.
단, 초심자는 테스트 설계를 처음부터 모두 수행하지 않는다.
초반에는 미리 준비된 시나리오를 통해 배운다.
이후 플레이어가 테스트 조건을 직접 선택하고 기대 결과를 예상하도록 한다.
플레이어가 요구사항을 바탕으로 로직을 구성한다.
예시:
"브레이크를 밟고 시스템이 준비된 경우에만 READY 상태로 전환되도록 만드세요."
입력과 출력의 관계를 구성한다.
테스트 담당 캐릭터가 질문한다.
"브레이크를 안 밟아도 시동이 걸리면 어떡하지?"
플레이어는 다음과 같은 테스트 조건을 선택한다.
- 브레이크 입력 없음
- 시스템 준비 안 됨
- 정상 시동 조건
- 전원 버튼 입력 없음
각 테스트에서 예상 결과를 선택하거나 확인한다.
테스트 엔진은 실제 실행 결과를 비교한다.
테스트가 실패하면 문제를 추적하도록 한다.
기본 화면에는 다음을 보여준다.
- 시험한 조건
- 예상 결과
- 실제 결과
- 잘못된 동작
- 관련 입력과 로직
플레이어가 원인을 추론할 수 있도록 정보를 단계적으로 제공한다.
플레이어가 로직을 수정하면 실패했던 테스트만 재실행하는 것이 아니라 이전에 통과한 테스트도 다시 실행할 수 있게 한다.
이를 통해 수정이 다른 기능을 손상시킬 수 있다는 개념을 학습한다.
미션의 주요 보상은 기능 완성과 검증 결과를 결합한다.
기능 작동
정상 동작 시나리오 통과.
기능 검증 완료
필수 테스트 통과.
검증 마스터

검증을 건너뛰면 완성된 차량 기능으로 확정하지 않는다.
플레이어가 만든 로직을 그대로 정답 기준으로 사용하지 않는다.
테스트의 기대 결과는 별도의 검수된 요구사항에서 정의한다.
테스트 엔진과 로직 실행 엔진은 분리한다.
플레이어가 로직을 바꾸어도 요구사항의 기대 결과는 자동으로 바뀌지 않아야 한다.
이 원칙은 기술 포트폴리오의 신뢰성을 확보하는 핵심이다.
게임의 학습 기준은 기능 중심이다.
차량 기능이 무엇을 하고 어떤 원리로 동작하는지 먼저 설명한다.
시스템·E/E·SW·물리 아키텍처는 해당 기능과 연결되는 정보를 단계적으로 표시한다.

## 11.4 그래픽 아트 디렉션

게임의 목표 품질은 **닌텐도 스위치에서 판매되는 완성도 높은 캐주얼 시뮬레이션 게임 수준의 시각적 일관성과 조작감**이다.

단순한 교육용 웹사이트나 공학 도구의 외형을 지양한다.

### 핵심 비주얼 콘셉트

- 아늑한 미니어처 자동차 정비소
- 둥글고 귀여운 장난감 자동차
- 크림·민트·살구·연분홍 중심의 부드러운 색상
- 밝고 따뜻한 조명
- 표정이 풍부한 오리지널 정비 캐릭터
- 과장된 물리 애니메이션
- 부드러운 UI 전환
- 정돈되고 명확한 로직 퍼즐 화면

동물의 숲과 치이카와에서 참고할 요소는 아늑함, 단순한 형태, 귀여운 리액션, 부담 없는 세계관이다.

기존 작품의 캐릭터, 에셋, UI 구성 및 고유한 디자인을 그대로 복제하지 않는다.

### 공간별 디자인

**정비소**

플레이어의 메인 허브다.

수리 중인 차량, 공구함, 작은 리프트, 작업대, 부품 선반, 테스트 장치가 존재한다.

미션을 완료할수록 정비소와 차량에 시각적인 변화가 발생한다.

**로직 작업대**

기존 Canvas를 재사용한다.

배경은 연한 그리드로 구성하고 블록은 둥근 사각형으로 표현한다.

연결 포트와 신호 흐름은 색상과 아이콘으로 명확하게 구분한다.

귀여운 스타일을 적용하더라도 블록 연결의 정확성과 가독성을 우선한다.

**테스트 공간**

완성된 기능을 실행해보는 공간이다.

READY 기능에서는 차량 계기판과 구동 준비 표시가 반응한다.

가속이나 제동 기능이 추가되면 차량 움직임까지 표현한다.

**테스트 트랙**

기존 레이싱 게임을 재사용한다.

처음에는 오프닝과 기본 주행 체험에 사용하고, 이후 로직과 실제 차량 거동을 연결한다.

### 그래픽 품질 기준

- 모든 주요 화면에 통일된 아트 스타일 적용
- 고해상도 차량 그래픽 사용
- 텍스트와 아이콘의 일관성 유지
- 차량 및 UI의 부드러운 상태 변화
- 명확한 조작 피드백
- 움직임에 어울리는 효과음
- 과도하지 않은 파티클 효과
- 캐릭터 리액션과 기능 성공 연출 제공
- 시뮬레이션 값과 애니메이션 상태 일치

그래픽 자산이 부족한 경우 무분별하게 임시 이미지를 생성해 채우지 않는다.

필요한 자산을 별도 목록으로 관리하고 `추가 예정` 상태로 등록한다.

## 11.5 차량 시각화와 실제 로직 연동

차량 애니메이션은 플레이어가 만든 로직의 실제 결과를 사용해야 한다.

연동 구조:

```text
플레이어 입력
    ↓
로직 그래프 계산
    ↓
출력 신호 / 차량 상태
    ↓
시뮬레이션 상태 갱신
    ↓
차량 그래픽 / 계기판 / 효과음
```

예시:

- 브레이크 입력 → 페달 애니메이션
- READY 진입 조건 충족 → 진입 요청 신호 활성화
- 상태 머신 READY 전이 → READY 표시등 점등
- 테스트 실패 → 실패한 조건 및 관련 블록 강조
- 검증 완료 → 차량 기능 복구 연출

READY 진입 요청과 실제 READY 상태는 서로 구분한다.

실제 상태 머신이 READY로 전이하지 않았다면 계기판에 READY가 표시되어서는 안 된다.

그래픽 재생 속도나 프레임 속도가 테스트 결과를 변경해서는 안 된다.

# 12. 검증 중심 게임플레이 설계

## 12.1 가장 중요한 변경사항

이 게임은 검증 관련 프로젝트이므로 로직 제작만으로 미션이 끝나서는 안 된다.

핵심 게임플레이는 다음 두 활동으로 구성한다.

**기능 제작**

플레이어가 차량 제어 로직을 구성한다.

**기능 검증**

플레이어가 해당 로직을 다양한 조건에서 테스트하고 결과를 판단한다.

두 활동이 하나의 미션에 자연스럽게 연결되어야 한다.

## 12.2 검증 플레이 흐름

1. 기능 요구사항 확인
2. 입력과 출력 관계 이해
3. 로직 조립
4. 정상 동작 관찰
5. 테스트 조건 선택
6. 예상 결과 판단
7. 테스트 실행
8. 실제 결과 확인
9. 실패 원인 분석
10. 로직 수정
11. 회귀 테스트
12. 기능 승인

초기 튜토리얼에서는 테스트 조건과 기대값을 일부 제공한다.

이후 미션에서는 플레이어가 테스트 조건 또는 예상 결과를 직접 선택하도록 한다.

## 12.3 테스트 선택 퍼즐

테스트를 단순히 자동 실행하는 버튼으로 만들지 않는다.

플레이어에게 다음 질문을 제시할 수 있다.

"어떤 상황에서도 잘못된 READY 진입이 발생하지 않는지 확인하려면 무엇을 시험해야 할까?"

선택 가능한 테스트:

- 브레이크를 밟고 시동 걸기
- 브레이크를 밟지 않고 시동 걸기
- 시스템 준비가 완료되지 않았을 때 시동 걸기
- READY 상태에서 전원 끄기

플레이어는 적절한 테스트를 선택하고 실행한다.

이때 테스트 선택의 이유도 짧게 설명한다.

## 12.4 정답 판정의 독립성

플레이어가 만든 로직을 기준으로 기대 결과를 자동 생성하지 않는다.

검증 엔진은 별도로 정의된 요구사항과 판정 기준을 사용한다.

```text
요구사항
  ├─ 기대 결과
  └─ 테스트 조건

플레이어가 만든 로직
  └─ 실제 결과

기대 결과 ↔ 실제 결과
          ↓
       PASS / FAIL
```

플레이어가 예상 결과를 선택한 경우에도 공식 판정 기준과 별도로 비교한다.

플레이어가 잘못 예상했다고 해서 실제 로직의 실행 결과를 변경하지 않는다.

## 12.5 테스트 실패 피드백

실패 시 다음 정보를 제공한다.

**기본 화면**

- 어떤 상황에서 실패했는가?
- 어떤 결과가 나와야 했는가?
- 실제로 어떤 결과가 발생했는가?
- 어느 입력 또는 조건을 확인해야 하는가?

**상세 화면**

- 관련 신호
- 현재 상태
- 상태 전이 조건
- 실행 순서
- 계산 결과
- 요구사항과의 연결

초급 미션에서는 한 번에 모든 로그를 제공하지 않는다.

## 12.6 회귀 검증

플레이어가 로직을 수정한 뒤 기존 테스트를 다시 실행할 수 있어야 한다.

수정한 문제가 해결되었더라도 이전에 통과했던 테스트가 실패할 수 있다는 사실을 학습시키기 위함이다.

예시:

브레이크 조건을 추가해 잘못된 READY 진입 문제를 해결했다.

이후 정상 시동 테스트도 여전히 통과하는지 확인한다.

**회귀 테스트는 별도 미니게임이 아니라 로직 수정 이후 자연스럽게 수행하는 행동으로 구현한다.**

## 12.7 검증 증거 기록

다음 데이터를 저장할 수 있어야 한다.

- 실행한 요구사항
- 테스트 입력
- 초기 상태
- 예상 결과
- 실제 결과
- 판정
- 사용한 로직 버전
- 시뮬레이션 설정
- 실행 시각 또는 실행 순서

저장 목적은 테스트 결과의 재현과 비교다.

개발용 데이터는 일반 플레이어에게 모두 노출하지 않는다.

## 12.8 검증 수준별 확장

| 단계 | 플레이어가 수행할 검증 | 게임 콘텐츠 |
|---|---|---|
| 기초 | 단일 로직 확인 | AND, 비교, 제한 |
| 상태 기반 | 상태 전이 확인 | READY, 충전 상태 |
| 연동 | 기능 간 입출력 확인 | VCU-BMS 정보 연동 |
| 타이밍 | 갱신 지연·Timeout | 통신 및 감지 지연 |
| 시스템 | 복수 기능 협조 확인 | 구동·제동 통합 |
| 심화 | 고장 주입과 회귀 검증 | 진단 및 안전 대응 |

이는 교육상 난도 분류다. 실제 검증 환경의 MIL/SIL/HIL 구분과 혼동하지 않는다.

# 13. 게임 스토리 및 플레이 흐름

## 13.1 기본 세계관

플레이어는 작은 정비소에서 귀여운 실험용 전기차를 관리한다.

차량은 시험 주행 도중 우스꽝스러운 사고를 당한다.

충돌과 함께 부품들이 만화처럼 튀어나오고 차량이 정비소로 돌아온다.

정비 캐릭터는 차량을 다시 달리게 만들기 위해 기능을 하나씩 복구하자고 제안한다.

차량의 외관 파손은 코믹한 스토리 연출이다.

실제 학습 대상은 차량의 제어 기능과 검증 과정이다.

기계적 파손이 SW 로직 수정만으로 복구된다고 설명하지 않는다.

## 13.2 최초 사용자 경험

### 장면 1 — 테스트 트랙

플레이어는 차량을 직접 조작한다.

조작은 기존 레이싱 게임의 입력 시스템을 재사용한다.

짧은 주행 후 미리 준비된 코믹한 사고 이벤트가 발생한다.

운전자의 잘못된 조작 때문에 실제 안전사고가 발생한 것처럼 표현하지 않는다.

### 장면 2 — 정비소

차량이 정비소에 도착한다.

외형은 귀엽게 망가진 상태다.

플레이어에게 현재 기능 상태를 보여준다.

- 구동 준비: 미완성
- 가속 제어: 추가 예정
- 제동 제어: 추가 예정
- 충전 관리: 추가 예정

실제 구현되지 않은 기능은 완성된 것처럼 표시하지 않는다.

### 장면 3 — 첫 번째 미션

"차가 주행 준비 상태가 되지 않아요!"

플레이어가 READY 기능을 학습한다.

### 장면 4 — 로직 조립

정비소의 작업대를 선택하면 로직 Canvas가 열린다.

입력과 출력에 맞게 블록을 연결한다.

### 장면 5 — 테스트

시동 조건을 바꿔가며 시험한다.

잘못된 조건에서는 READY가 켜지지 않아야 한다.

### 장면 6 — 복구 완료

필수 검증을 통과하면 차량의 READY 기능이 활성화된다.

정비 캐릭터의 리액션과 함께 계기판이 켜진다.

### 장면 7 — 테스트 트랙

차량의 복구 상태를 확인한다.

초기 버전에서는 READY 표시와 주행 가능 상태의 차이를 설명한다.

실제 가속·제동 로직을 게임 내에서 구현해 차량 움직임과 연결하는 기능은 후속 개발로 분리한다.

기존 레이싱 게임이 독립적으로 작동한다면 해당 모드는 보존한다.

## 13.3 개별 미션 진행 구조

```text
차량에 문제가 생김
        ↓
정비소에서 상황 확인
        ↓
정상 동작 시범
        ↓
기능 설명
        ↓
로직 조립 퍼즐
        ↓
작동 시험
        ↓
검증 시나리오
        ↓
실패 시 수정
        ↓
모든 필수 테스트 통과
        ↓
차량 기능 복구
        ↓
보상 및 다음 미션
```

## 13.4 고장 추리게임 재활용

기존 고장 추리게임은 새로운 미션의 후반 챌린지로 재구성한다.

단, 학습한 기능에 대해서만 고장 원인 분석을 진행하도록 한다.

추리의 핵심은 정답을 짐작하는 것이 아니라 **추가 관측이나 테스트로 가능한 원인을 좁히는 것**이다.

예시:

- READY 미활성화
- 브레이크 입력 확인
- 시스템 준비 상태 확인
- 상태 전이 조건 확인
- 원인 후보 축소
- 수정 및 재검증

초기 버전에서는 `추가 예정 — 고장 분석 챌린지`로 관리한다.

# 14. 재미와 학습을 결합하는 UX 설계

## 14.1 목표

학습 콘텐츠를 게임 외부의 설명 자료처럼 제공하지 않는다.

플레이어가 목표를 달성하기 위해 자연스럽게 개념을 이해하도록 설계한다.

## 14.2 학습 난도

초기에는 다음 조건을 지킨다.

- 새 개념은 미션당 1~2개로 제한
- 처음 보는 전문 용어는 짧게 설명
- 정상 동작을 먼저 관찰
- 사용 가능한 블록 수 제한
- 복잡한 아키텍처 정보 숨김
- 실패 시 즉각적 피드백 제공
- 이전 미션에서 배운 개념 반복 활용

고급 단계에서는 지원을 점차 줄인다.

플레이어가 스스로 입력 조건과 검증 방법을 판단하도록 유도한다.

## 14.3 재미를 만드는 핵심 요소

**예측**

플레이어가 로직의 결과를 예상한다.

**조작**

실제로 입력을 바꾸거나 블록을 연결한다.

**반응**

차량 상태와 신호가 즉시 반응한다.

**발견**

예상과 실제 결과의 차이를 발견한다.

**수정**

직접 문제를 개선한다.

**성취**

차량 기능이 활성화되고 다음 기능을 사용할 수 있다.

이 흐름을 기본 게임 루프로 유지한다.

## 14.4 보상 시스템

핵심 보상은 가상의 돈이나 경험치가 아니라 차량의 변화다.

- 기능 복구 애니메이션
- 검증 완료 스탬프
- 차량 상태 개선
- 새 기능 해금
- 정비소 변화
- 캐릭터 리액션
- 테스트 트랙에서의 새로운 동작

별점이나 배지는 보조 요소로만 사용한다.

## 14.5 코믹한 연출

게임의 재미를 위해 다음 효과를 사용할 수 있다.

- 차량이 통통 튀는 효과
- 범퍼가 뿅 하고 빠지는 애니메이션
- 정비 캐릭터의 당황한 표정
- 작동 실패 시 과장된 기계음
- 기능 복구 시 경쾌한 성공음
- 테스트 성공 후 차량의 귀여운 반응

단, 실제 검증 결과 자체를 희화화하지 않는다.

특히 위험 상황, 제어 불능, 기능안전 실패를 다루는 교육 콘텐츠에서는 기술적 사실과 코믹한 표현을 명확하게 구분한다.

## 14.6 접근성

- 주요 입력은 마우스로 조작 가능
- 드래그 외에 클릭 연결도 지원할 수 있도록 설계
- 글자 크기와 대비 확보
- 색상 이외의 상태 표시 사용
- 애니메이션 감소 설정
- 효과음 음량 조절
- 퍼즐 초기화
- 실행 취소
- 힌트 제공

# 15. 자동차 도메인 확장 및 아키텍처

## 15.1 범용성

게임 엔진은 특정 EV 기능에 의존하지 않아야 한다.

확장 대상:

- 구동
- 배터리
- 충전
- 제동
- 조향
- 열관리
- 차체 제어
- ADAS
- 진단
- 차량 네트워크

## 15.2 아키텍처 관점 구분

게임의 주 관점은 기능 아키텍처다.

기능 아키텍처는 차량이 무엇을 수행하는지 설명한다.

E/E 아키텍처는 해당 기능이 어떤 ECU, 센서, 액추에이터, 네트워크, 전원 구조로 구현되는지 설명한다.

E/E는 논리적인 기능 할당과 물리적인 전장 연결을 모두 포함한다.

기능과 E/E를 단일한 상하 레이어로 취급하지 않는다.

SW 아키텍처는 로직의 구현 구조를 나타내고, 물리 모델은 실제 차량 반응을 나타낸다.

## 15.3 기능 추가 방식

각 기능은 다음 항목을 등록한다.

- 학습 목표
- 입력
- 출력
- 정상 동작 시나리오
- 요구사항
- 사용 가능한 블록
- 테스트 조건
- 기대 결과
- 시각화 종류
- 관련 아키텍처
- 완료 보상

새로운 기능이 기존 공통 블록으로 표현 가능하다면 게임 엔진 수정 없이 콘텐츠 데이터로 추가한다.

새로운 연산 또는 물리 모델이 필요할 때만 확장 인터페이스를 사용한다.

## 15.4 아키텍처 오버레이

플레이어는 기능을 완료한 후 해당 기능이 실제 차량에서 어디에 해당하는지 확인할 수 있다.

기본 보기:

- 기능 이름
- 역할
- 입력 및 출력
- 관련 시스템
- 검증한 동작

상세 보기:

- 관련 ECU
- 센서 및 액추에이터
- 관련 SW 구성요소
- 인터페이스
- 통신 및 신호 정보

검수되지 않은 자료는 표시하지 않거나 학습용 가상 모델임을 명시한다.

# 16. 기능안전 콘텐츠 설계

## 16.1 적용 목적

기능안전을 모든 고장에 붙이는 장식적 키워드로 사용하지 않는다.

정상 기능에서 어떤 이상 동작이 발생할 수 있으며, 필요한 경우 이를 어떤 안전 요구사항 및 안전 메커니즘으로 통제하는지 학습하도록 한다.

## 16.2 학습 단계

1. 정상 기능 이해
2. 기능의 오동작 사례 이해
3. 위험 상황과 일반적인 기능 실패 구분
4. 관련 안전 목표 및 요구사항의 역할 이해
5. 안전 메커니즘 로직 구성
6. 정상·이상 조건 검증
7. 재검증 및 결과 분석

## 16.3 심화 콘텐츠 예시

가속 페달 신호의 이상 감지와 토크 제한.

가상 차량에서 다음 조건을 정의할 수 있다.

- 입력 신호가 정의된 유효 범위를 벗어남
- 두 입력 정보가 허용된 차이를 초과함
- 이상 상태가 일정 조건을 만족함
- 해당 상태에서 정의된 제한 동작을 수행함

이는 기능안전 관련 개념을 학습하기 위한 예시다.

위험 분석 없이 임의의 ASIL 등급을 지정하지 않는다.

## 16.4 표준과 실제 구현의 구분

ISO 26262 개념을 교육에 적용하는 것과 해당 표준의 요구사항을 충족하는 것은 별개다.

게임은 실제 인증 또는 양산 안전성을 증명하는 도구가 아니다.

실제 HARA, FSC, TSC, 안전 요구사항 및 검증 산출물을 모두 수행했다고 표현하지 않는다.

**기능안전 콘텐츠는 첫 MVP에 포함하지 않는다.**

추가 예정으로 관리하며, 안전 요구사항 및 검증 근거가 준비된 이후 구현한다.

# 17. 기존 프로젝트 및 데이터 재사용

## 17.1 재사용 원칙

기존 프로젝트 자산을 먼저 분석한다.

중복 구현과 불필요한 삭제를 방지한다.

우선 조사 대상:

- Canvas
- 노드 및 연결선
- 레이싱 조작 시스템
- 차량 그래픽
- 기존 물리 모델
- 고장 추리 콘텐츠
- 요구사항
- 인터페이스
- 신호 정의
- 아키텍처 정보
- 테스트 케이스
- 로그 및 시뮬레이션

## 17.2 기존 자료 검수

기존 요구사항과 아키텍처 정보를 무조건 폐기하지 않는다.

다만 검수되지 않은 자료를 정식 게임의 정답으로 사용하지 않는다.

자료 상태:

- 검수 완료
- 검수 대기
- 오류 확인
- 사용 보류

검수 시 확인:

- 차량 기능의 정의
- 신호의 의미 및 단위
- 입력·출력 관계
- 상태 전이 조건
- 인터페이스 방향
- 요구사항의 테스트 가능성
- 실제 사양과 가상 사양의 구분
- 기존 데이터 간 모순

## 17.3 교육용 데이터로 변환

기존 자료를 다음과 같이 활용한다.

- 요구사항 → 미션 목표 및 검증 기준
- 신호 → 로직 입력·출력
- 인터페이스 → 연결 관계
- ECU 정보 → 아키텍처 오버레이
- 고장 시나리오 → 심화 검증
- 로그 → 실행 결과와 비교 자료

처음부터 전체 데이터를 화면에 노출하지 않는다.

## 17.4 플레이어 정보 표시

개발용 ID는 내부에서만 사용한다.

기본 화면에는 쉬운 한글 표현을 표시한다.

예시:

- `REQ-READY-001` → 시동 준비 조건
- `Brake_Pressed` → 브레이크 페달
- `System_OK` → 시스템 준비 완료
- `TC-READY-03` → 브레이크 없이 시동 걸기

전문 용어는 학습이 필요한 경우에만 설명과 함께 제공한다.

# 18. 기술 구현 원칙

## 18.1 필수 구조

```text
Mission / Requirements
          ↓
     Logic Canvas
          ↓
     Logic Engine
          ↓
   Simulation Engine
       ↙       ↘
Verification   Visualization
       ↘       ↙
     Progress / Rewards
```

## 18.2 엔진 분리

다음 시스템을 분리한다.

- 콘텐츠
- Canvas 편집
- 블록 실행
- 상태 머신
- 테스트
- 시뮬레이션
- 차량 물리 모델
- 시각화
- 진행 및 보상

그래픽 프레임 속도와 테스트 실행 결과는 독립적이어야 한다.

## 18.3 테스트 재현성

동일한 입력, 초기 상태, 실행 설정, 로직 버전은 동일한 결과를 생성해야 한다.

테스트마다 실행 전 필요한 내부 상태를 초기화한다.

테스트 결과는 실행 순서나 이전 테스트의 잔여 상태에 의존하지 않아야 한다. 연속 동작을 시험하는 경우에는 의도적인 상태 유지가 명시되어야 한다.

## 18.4 지원할 신호 정보

기본 신호:

- Boolean
- Number
- Enum
- Event

확장 신호 정보:

- 단위
- 유효 범위
- 갱신 시각
- 유효성
- 신호 출처
- 주기 또는 지연 정보

## 18.5 기존 레이싱 연동

레이싱 연동은 어댑터 방식으로 구성한다.

로직 엔진의 출력이 차량 구동 명령으로 전달되고, 차량 시뮬레이션의 상태가 로직 입력에 반영될 수 있도록 한다.

초기에는 기존 레이싱 엔진을 직접 재작성하지 않는다.

연동 가능 여부를 분석한 뒤 별도 작업으로 구현한다.

# 21. 교육 효과 평가

## 21.1 평가 목적

게임을 완료하는 것이 실제 차량 기능 이해로 이어지는지 확인한다.

## 21.2 평가 항목

**도메인 이해**

학습자가 READY 상태의 의미와 진입 조건을 설명할 수 있는가?

**로직 이해**

처음 보는 입력 조건을 주었을 때 예상 출력을 판단할 수 있는가?

**검증 이해**

정상 조건뿐 아니라 부정 조건도 확인해야 하는 이유를 설명할 수 있는가?

**전이 학습**

기존 미션에서 배운 논리와 검증 방법을 다른 기능에도 적용할 수 있는가?

## 21.3 권장 평가 방식

- 학습 전 간단한 개념 확인
- 미션 수행
- 학습 직후 새로운 조건의 문제 해결
- 이전 미션과 다른 조건에서 동일 개념 재적용
- 선택적으로 시간 간격을 둔 재평가

게임 플레이 시간이나 점수만으로 학습 효과를 판단하지 않는다.

## 21.4 UX 평가

테스트 사용자에게 다음 항목을 확인한다.

- 게임 목표를 이해했는가?
- 블록을 직관적으로 연결할 수 있었는가?
- 테스트 실패 이유를 이해했는가?
- 그래픽이 동작 원리 이해에 도움이 되었는가?
- 다음 미션을 자발적으로 플레이하고 싶었는가?
- 기술 설명이 지나치게 많았는가?
- 플레이가 지나치게 단순하거나 반복적이었는가?

가능하면 실제 초심자 사용자를 대상으로 테스트한다.

# 22. 기술 포트폴리오 구성

## 22.1 포트폴리오에서 강조할 핵심

이 프로젝트의 가치는 귀여운 차량 게임을 구현했다는 사실보다 다음 구조에 있다.

**요구사항 → 로직 모델링 → 시뮬레이션 → 테스트 설계 → 검증 → 결과 분석 → 회귀 검증**

게임 인터페이스는 해당 과정을 직관적으로 경험하도록 설계한 수단이다.

## 22.2 필수 기술 증빙

- 시스템 아키텍처
- 로직 엔진 구조
- 실제 실행되는 블록 예시
- 요구사항 예시
- 테스트 케이스 예시
- 기대 결과와 실제 결과 비교
- 의도적으로 잘못된 로직의 실패 사례
- 수정 후 재검증 사례
- 재현 가능한 실행 방법
- 게임 시연 영상

## 22.3 정확한 기술 표현

사용 가능한 표현:

- 차량 기능 학습용 로직 시뮬레이터
- 요구사항 기반 테스트 엔진
- 상태 머신 실행 및 검증
- 교육용 가상 차량 모델
- 테스트 시나리오 자동 실행
- 기능 간 인터페이스 시뮬레이션(실제 구현한 경우)

주의할 표현:

- ISO 26262 준수 검증 도구
- 양산 ECU 검증 시스템
- HIL 검증
- 실제 차량과 동일한 물리 시뮬레이션
- ASIL 등급 확보
- AUTOSAR 기반 시스템 전체 구현

실제로 수행하지 않은 검증 환경이나 표준 적용을 주장하지 않는다.

## 22.4 실무 경험과 프로젝트의 관계

본 프로젝트는 기존 검증 실무를 대체하는 경험이 아니다.

실무에서 접한 요구사항, 검증, 결과 판정의 사고방식을 학습용 가상 차량 시스템에 적용해보는 독립적인 프로젝트다.

고객사 소스코드나 기밀 자료를 사용하지 않는다.

자체 제작한 교육용 사양과 테스트 데이터를 사용한다.

# 23. 품질 검증 및 최종 인수 기준

## 23.1 기능

- 플레이어가 실제로 블록을 조립할 수 있다.
- 연결에 따라 계산 결과가 달라진다.
- 잘못된 로직은 테스트에 실패한다.
- 수정된 로직은 동일 테스트에서 다시 평가된다.
- READY 상태 전이가 올바르게 처리된다.
- 화면의 READY 표시와 내부 상태가 일치한다.

## 23.2 게임

- 오프닝에서 게임 목표를 이해할 수 있다.
- 미션 수행 이유가 스토리와 연결된다.
- 정비소와 차량에 시각적인 변화가 있다.
- 미션 성공 시 명확한 보상이 있다.
- 사용자는 다시 시도하거나 이전 단계로 돌아갈 수 있다.

## 23.3 UX

- 내부 ID가 기본 화면에 과다 노출되지 않는다.
- 초급 미션은 핵심 정보만 보여준다.
- 오류 발생 시 수정해야 할 조건을 안내한다.
- Canvas는 확대·축소 및 재배치가 가능하다.
- 캐릭터 및 애니메이션이 정보 판독을 방해하지 않는다.

## 23.4 그래픽

- 일관된 스타일을 적용한다.
- 차량과 계기판 상태가 로직과 연동된다.
- 주요 버튼과 블록의 상호작용 피드백이 존재한다.
- 기본 화면에 눈에 띄는 임시 그래픽이나 미완성 배치가 남아 있지 않다.
- 고급 그래픽 미구현 항목은 명확하게 분리한다.

## 23.5 기술

- 시뮬레이션 결과의 재현성이 확보된다.
- 실행 엔진과 그래픽이 분리되어 있다.
- 테스트 판정 기준이 사용자 로직과 독립적이다.
- 기존 프로젝트 기능이 의도치 않게 손상되지 않았다.
- 다른 도메인의 간단한 기능을 공통 엔진에 등록할 수 있다.

# 24. 코딩 에이전트 최종 개발 지시

현재 프로젝트를 분석한 뒤, 기존 자산을 최대한 재사용하여 **Vehicle Logic Lab**을 구현하라.

게임의 장르는 차량 제어 기능을 조립하고 검증하는 캐주얼 엔지니어링 퍼즐 게임이다.

플레이어는 기존 레이싱 시스템을 이용한 짧은 주행 도중 만화적인 사고를 경험하고, 정비소에서 차량의 제어 기능을 하나씩 복구한다.

그래픽 방향은 아늑하고 귀여운 고품질 미니어처 게임 스타일이다.

로직 퍼즐은 기존 Canvas와 노드 시스템을 재사용한다.

게임의 핵심은 플레이어가 직접 블록을 연결하고, 로직의 실제 실행 결과를 확인하며, 다양한 테스트로 동작을 검증하는 과정이다.

**가장 중요한 구현 조건은 다음과 같다.**

1. 플레이어의 로직은 실제로 실행되어야 한다.
2. 테스트 기대 결과는 플레이어가 만든 로직과 독립적으로 정의해야 한다.
3. 로직 수정 후 재검증이 가능해야 한다.
4. 차량 그래픽은 실제 시뮬레이션 결과를 반영해야 한다.
5. 로직 제작과 검증을 모두 게임의 핵심 플레이로 구현해야 한다.
6. 기존 레이싱과 추리게임은 삭제하지 않고 재사용 가능한 상태로 보존해야 한다.
7. 신규 도메인 추가 시 공통 엔진을 재작성하지 않도록 설계해야 한다.
8. 기존 요구사항·신호·인터페이스·아키텍처 데이터는 검수 상태에 따라 관리해야 한다.
9. 플레이어에게 개발용 ID와 불필요한 기술 정보를 과도하게 노출해서는 안 된다.
10. 그래픽은 고품질을 지향하되 핵심 동작의 정확성을 희생해서는 안 된다.

### 현재 구현할 범위

- 짧은 레이싱 오프닝 또는 대체 사고 연출
- 기본 정비소
- READY 상태 제어 미션 3개
- 실제 실행 가능한 로직 Canvas
- Boolean 및 상태 전이 엔진
- 기본 테스트 검증
- 차량 계기판과 상태 연동
- 기능 복구 애니메이션
- 미션 완료 보상
- 진행 상태 저장

### 현재 구현하지 않을 범위

- 복잡한 차량 물리 모델 신규 개발
- 레이싱과 실시간 제어 로직의 전체 연동
- 방대한 차량 E/E 아키텍처 구현
- 모든 차량 도메인 콘텐츠
- 고급 타이밍 및 통신 검증
- 완전한 기능안전 분석
- 복잡한 고장 추리 미션
- 전면적인 3D 차량 그래픽

이 항목들은 `추가 예정`으로 관리한다.

# 25. 최종 프로젝트 정의

**게임 콘셉트**

망가진 꼬마 자동차를 직접 수리하고, 차량 제어 기능을 하나씩 완성해 다시 달리게 만드는 귀여운 로직 퍼즐 게임.

**학습 콘셉트**

차량의 정상 동작을 관찰하고, 요구사항에 맞게 로직을 구성한 뒤, 시뮬레이션과 검증을 통해 동작 원리를 이해하는 교육용 게임.

**기술 콘셉트**

차량 기능 아키텍처를 중심으로 요구사항, 실행 가능한 로직, 시뮬레이션, 테스트, 결과 분석을 연결하는 범용 검증 학습 플랫폼.

**개발 전략**

핵심 게임 루프 하나를 고품질로 완성하고, 이를 재사용하여 차량 도메인과 검증 수준을 확장한다.

**최종 원칙**

게임의 재미는 차량이 실제로 달라지는 경험에서 얻고, 교육 효과는 플레이어가 직접 로직을 구성하고 검증하는 과정에서 얻는다.

귀여운 시각적 표현과 공학적 정확성을 서로 대체하지 않고 함께 구현한다.
