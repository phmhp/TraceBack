# 차량 학습 흐름과 6가지 설계 관점 · 2026-10-29

## 이번 화면 설계 기준

기능 트리는 **차량이 수행하는 일**로 분해한다. System 아래 Domain은 에너지·전원, 구동, 제동, 조향, 차체·열·통합으로 나눈다. Domain 아래 묶음은 단계의 목적이다. 예를 들어 구동은 `요구·허용`(페달을 토크 요구로 바꾸고 구동 가능 여부 판단)과 `실현`(명령을 모터 토크와 바퀴 힘으로 변환)으로 구분한다. 그 아래 Function은 독립적인 입력·출력·동작 조건으로 시험할 수 있는 단위다. 이 기준은 `IntegratedArchitectureOverview.tsx`에 드러난다.

ECU / Application SWC / Runnable은 기능 트리의 자식 계층이 아니라 **기능을 실행 장치에 배치한 결과**다. 따라서 기능 위치와 실행 배치를 별도 줄에 표시한다. 현재 블록 편집기는 한 Function의 계산 경로를 다루며, `MODEL_ALLOCATION`의 Runnable 이름은 그 기능을 호출하는 실행 단위를 가리킨다. 화면의 블록 하나를 AUTOSAR Runnable 하나로 간주하지 않는다. 신규 사용자가 액추에이터까지의 인과관계를 익히는 첫 사이클은 Function 수준의 입출력과 요구 동작으로 충분하다. SWC/Runnable 상세, RTE/BSW 경계와 주기·이벤트는 고급 확장 단계로 다뤄야 한다.

첨부된 “설계 패턴의 6가지 레벨”은 하나의 수직 계층이 아니다. ① Distributed/Domain/Zonal은 차량 E/E 배치, ② Layered/Component는 ECU 내부 SW 책임, ③ Sender–Receiver/Client–Server는 통신 방식, ④ State/Strategy 등은 상세 SW 설계, ⑤ PID/State Machine/Lookup은 제어 계산 방식이다. ⑥ Redundancy/Monitoring/Failover는 앞의 모든 수준에 걸친 고장 대응이다. 게임은 첫 사이클에서 **기능 분해와 기능별 분산 ECU 배치**, 그리고 입력→Application 기능 계산→출력→액추에이터→차량 반응에 초점을 둔다. 나머지 패턴을 기능 트리의 하위 노드인 것처럼 놓지 않는다.

## 이번에 반영한 흐름

- 기술 선택 지도는 분야별 카드 안에 구성별 장치·제어 경계의 특징을 표시한다. 별도 비교 상자와 약어 목록은 제거했다.
- 기능 경로에서 전력/신호/기계 탭을 분리하지 않고, 선택한 Function의 입력→SW→출력 신호→액추에이터·기계→차량 반응을 순서대로 본다. 기능 트리는 기본으로 접힌다.
- EV 개조 결심을 앞·뒤 바퀴 장착보다 먼저 보여준다. 부품 선택은 해당 기능이 EV에서 작동하는 데 필요한 장치를 고르는 질문으로 시작한다. ICE/내연기관차 명칭을 사용한다.
- SW 편집기의 임시 단계형 개념 퀴즈를 삭제했다. 설명은 도움말 아래로 옮기고, 로직 실행에서는 계산 오류와 액추에이터 반응 차이를 먼저 보여준다. 블록 라이브러리는 화면 최상위 레이어로 열어 작업대의 크기·스크롤에 잘리지 않게 했다.
- 마지막 설계 지도에는 System→Domain→Function 선택을 항상 노출했다. 복구 실행 추적은 3초 간격으로 늦추고 현재 단계의 부품·연결을 3D에 전달한다.

## 아직 남은 제작 단위와 인수 기준

1. **전용 차량·액추에이터 3D 자산:** 배터리·인버터·모터·감속기·차동기어·제동 캘리퍼·EPS·배선의 실제 식별 가능한 형상, 분해도, 고양이 리깅을 같은 디자인 언어로 제작한다. 모든 카메라에서 관통과 글자 흐림이 없는지 GPU 실기 화면으로 검수한다. 현재는 기존 코드 3D의 강조·색·카메라를 개선한 상태다.
2. **Domain/Function 조립 퍼즐:** 부품의 실제 입력 센서와 출력 액추에이터 사이에 Domain과 Function 조각을 배치하고, 결과가 다른 도메인 구성에서도 성립하는지 행동으로 판정한다. 단순 명칭 퀴즈나 정답 위치 판정은 쓰지 않는다. `DomainEditor`의 신호 그래프와 실행 상태를 공유해야 한다.
3. **필수 기능 제작 에피소드:** 지금 직접 제작하는 8개 외에 프리차지·접촉기 상태기, 충전/OBC, DC/DC·12V, 열관리, 회생/마찰 배분·ABS/ESC, EPS 보조, 신호 진단을 각각 부품→신호/로직→고장 시험→같은 차량 물리 반응으로 이어야 한다. `vehicleSystems.ts` 계산과 읽기 전용 선택지는 제작 완료로 세지 않는다.
4. **실행 추적 확장:** 고장 조건별 ECU 송신/수신·버스 신호·BSW/RTE 경계, 시간축의 센서→Runnable→액추에이터 명령→물리 반응을 동일 tick으로 기록하고 3D 장치·배선에 재생한다. 현재는 제작 모델 출력과 일부 장치에 한정된다.
5. **블록 의미 검증:** 현재 39종은 게임 실행기의 이산 샘플 의미를 제공한다. MathWorks 블록의 파라미터 전체, 자료형·샘플 시간·다중 출력·Stateflow/SubSystem 동등성을 명세별로 대조해야 한다. 화면에서 모양이 닮은 것과 동일 기능 판정은 별개다.
6. **신입 사용자 검수:** 첫 플레이 3명 이상에게 질문 없이 START·부품 선택·블록 연결·실행 추적·설계 지도 탐색을 수행하게 하고, 어디에서 기능 분해와 ECU 실행 배치를 혼동하는지 기록한다. 현재 자동 검사는 UX 학습 효과를 증명하지 않는다.
