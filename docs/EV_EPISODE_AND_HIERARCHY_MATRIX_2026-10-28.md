# EV 전체 기능·실행 배치·에피소드 매트릭스

**2026-10-29 갱신:** BMS의 `PackSafe`와 VCU의 `StartPermit`은 플레이어 제작 기능이 됐다. 직접 구성 모델은 8개다. 배터리 가용 토크 산정과 접촉기·프리차지 상태전이는 별도 차량 상태 계산이며 제작 완료로 세지 않는다.

2026-10-28. 제작·검수용 문서. 상태는 저장소의 실제 코드와 게임 흐름 기준이다. 플레이어 화면에는 구현 범위에 대한 단서 대신 현재 과제, 입출력, 장치 반응을 보여준다.

## 기준 차량과 두 개의 경로

기준 차량은 **고전압 배터리, 단일 후륜 구동 모터, 앞바퀴 기계식 랙 + EPS, 회생·마찰 협조 제동, 기능별 분산 제어기**를 갖는다. 이 배치는 게임의 한 차량 사양이지 모든 제조사의 공통 배치가 아니다. 다른 구동축·모터 수·조향·제어기 통합 방식은 별도 차량 시나리오로 저장해야 한다. 구동축을 선택만 바꾸고 동일 물리·로직을 재사용하면 잘못된 학습이 된다.

```text
기능을 찾는 경로:  System / Domain / Function / 요구 동작
실행 위치 경로:   ECU / Application SWC / Runnable / 입출력 포트
물리 경로:       에너지 또는 운전자 힘 / 센서·제어 / 액추에이터 / 바퀴·차체
검증 경로:       단위 / ECU 간 통합 / 임베디드·HIL / 차량
```

Domain은 ECU의 상위 폴더가 아니다. 전력 허용, 토크 요청, 인터록은 모두 VCU에 있을 수 있다. 제동 협조 기능은 제동 ECU의 요청과 VCU·인버터의 회생 한계를 함께 사용한다. 기능·E/E·물리·SW·검증은 동일한 차량을 보는 다섯 관점이다. AUTOSAR Classic의 Application, RTE, BSW는 ECU 내부 소프트웨어 계층이며 기능 도메인 계층과 다르다([AUTOSAR Classic Platform](https://www.autosar.org/standards/classic-platform/)).

## System → Domain → Function → ECU/SWC/Runnable 및 현재 상태

표의 `제작`은 플레이어가 그래프를 직접 구성하고 독립 사례로 시험한 기능이다. `계산`은 `vehicleSystems.ts`가 값을 계산하지만 제작 미션은 없는 기능이다. `장치`는 조립 또는 3D 표시가 있는 상태다. `없음`은 그 연결이 없다. 물리 전달처럼 소프트웨어가 없는 항목은 SWC/Runnable을 만들지 않는다.

이 표는 **정상 주행·정차·충전·저전압·열 보호·기본 안정 제어**의 기준 차량 범위다. 등화, 와이퍼, 인포테인먼트, ADAS, 에어백 같은 별도 차량 기능 전체를 포함한다는 뜻은 아니다. 필수 범위의 세부 센서, 고장·우회 전략, 타이밍은 각 에피소드 요구사항에서 다시 고정해야 한다. 배터리, 모터, OBC, DC/DC 및 열관리 장치의 구분은 [미국 DOE AFDC의 BEV 구성 안내](https://afdc.energy.gov/vehicles/how-do-all-electric-cars-work)를 참고했다.

## 한 게임 사이클 뒤에 이어질 에피소드 계약

각 에피소드는 **차고 → 작동 관찰 → 부품·배선 선택·장착 → SWC/Runnable 구성 → 정상·경계·고장 시험 → 동일 3D 차량 반응 → 기능 추적 → 차고 복귀**를 완주해야 저장된 차량에 기능을 추가한다. 현재 게임은 에피소드 1·3·4·5·7의 일부 기능만 한 사이클에 묶어 두었으므로 아래 표의 에피소드는 아직 완성된 플레이 흐름이 아니다.

| 에피소드 | 플레이어가 만드는 것 | 선택지와 달라지는 시험 | 완료 상태 |
|---|---|---|---|
| 1. READY와 고전압 | BMS 상태 판단, 접촉기·프리차지 순서, 차량 모드·전력 사용 허용 | 잔량·온도·절연·전압·시동 조건 | BMS PackSafe·VCU START 허용·전력 허용 제작; 접촉기·프리차지 상태전이 제작 미완료 |
| 2. 충전·12V·열 | OBC 충전 허용, DC/DC 공급, 냉각 펌프·팬과 출력 제한 | 충전 연결, 온도, 저전압 부하 | 시스템 계산만 있음 |
| 3. 구동 | 페달 유효성, 토크 요청·상한·인터록, 인버터 토크 추종 | 기준 후륜과 이후 전륜·듀얼 모터; 구동축·토크 배분 시험 분리 | 요청·인터록 제작 |
| 4. 제동 | 제동력 요청, 회생 가능량·마찰 배분, 휠별 ABS/EBD/ESC | 충전 가능 여부, 저속, 슬립, 요 오차 | 마찰력 요청 제작 |
| 5. 조향 | 전륜 각도, 운전자 토크와 EPS 보조 전류·고장 처리 | 기준 기계 연결 EPS; 별도 Steer-by-Wire 차량은 이중화·고장 전략 새로 설계 | 각도 변환만 제작 |
| 6. 섀시 | 앞뒤 바퀴·현가·접지 경로와 차량 운동을 조립·시험 | 타이어·노면·하중 변화, 휠별 접지 확인 | 네 바퀴 장착·기본 주행 |
| 7. E/E 통합·진단 | ECU별 송수신 포트, 신호 주기·유효성·타임아웃, 액추에이터 연결 | 분산 ECU 기준; 도메인 통합/존형은 별도 배치와 시험 | 라우팅 제작 |

차량 선택 지도는 현재 기준 차를 표시한다. 선택지가 실제 차량을 바꾸려면 저장 데이터의 사양 ID와 함께 조립 부품, 시스템 계산, ECU 할당, 시험 사례, 3D 모델, 설계 지도까지 변해야 한다. 설명 카드만 바뀌는 옵션은 새로운 차량으로 계산하지 않는다.

## ICE → EV를 플레이 중에 보여주는 규칙

현재 부품 파악 단계에는 에너지, 구동, 제동, 조향 각각 **이전 차의 경로 → 바뀌는 역할 → EV의 경로 → 네 칸 실행 흐름**과 흰둥의 짧은 말풍선을 넣었다. 후속 구현에서는 각 단계의 실제 상태 신호에 맞춰 전력선, 모터축, 캘리퍼, EPS 랙만 순서대로 움직이게 한다.

| 관찰 | ICE 쪽에서 제거·변경 | EV에서 장착·추가 | 유지되는 물리 경로 |
|---|---|---|---|
| 에너지·시동 | 연료 저장·연소 시동 경로 | 배터리, BMS, 접촉기·프리차지, OBC, DC/DC | 12V 전장과 운전자 시동 요구 |
| 추진 | 엔진과 배기 경로 | 인버터, 모터, 감속기 | 구동축, 타이어, 노면 |
| 감속 | 연소기관 제동 의존을 줄임 | 회생 토크와 마찰 제동 협조 | 캘리퍼·디스크·페달 |
| 조향 | 엔진 구동식 보조장치가 있는 차량이라면 대체 | EPS 보조 모터·제어기 | 기준 차량의 운전대·조향축·랙 기계 연결 |

ICE의 흡기→압축→연소·동력→배기와 대응하여 EV는 **배터리 상태 확인→고전압 경로 준비→인버터 전류·모터 토크→감속기·바퀴 힘 전달→회생 시 에너지 귀환**의 동작을 짧은 반복 장면으로 보여준다. EV에 ICE의 네 행정을 억지로 1:1 대응시키지 않는다. 애니메이션의 활성 상태와 숫자는 임의 타이머가 아니라 같은 시스템 프레임에서 받아야 한다. 영상 링크는 사용자 참고 자료이며 영상의 특정 프레임을 검증했다는 뜻은 아니다.

## 다섯 관점과 AUTOSAR 탐색기

최종 설계 지도는 기능·물리·E/E·SW·검증 탭 각각에 네 노드 연결도를 현재 도메인별로 보여준다. 단계 재생이 해당 노드와 3D의 선택 부품을 강조한다. SW 탭의 파일 탐색기는 `VehicleSystem.arxml`, `Composition.arxml`, `EcuExtract.arxml`, `SwcDescription.arxml`, 생성 RTE, BSW 설정, Application SWC 소스가 어떤 역할인지 클릭해서 설명한다. **폴더와 파일명은 이 차량 프로젝트의 예시**이며 AUTOSAR의 강제 디렉터리 규칙이라고 가르치지 않는다. 실제 프로젝트 교재가 되려면 ARXML 요소, ECU Extract, Runnable 이벤트, 포트·데이터 타입, RTE 생성물과 소스 매핑을 더 구체화해야 한다.

## 검증 학습 효과에 대한 냉정한 판정

| 수준 | 현재 실제로 해 볼 수 있는 것 | 부족한 것 | 현 단계 판정 |
|---|---|---|---|
| 단위 | 8개 그래프에 독립 입력·예상 출력 사례; 틀리면 값 비교 | 경계값 도출·테스트 설계는 대부분 제공됨 | **부분 충족** |
| ECU 간 통합 | 제작 토크·제동·조향 출력이 차량 물리 명령에 도달; 3D 수치 확인 | 신호 소유자·주기·타임아웃·실제 ECU 포트 계약 | **부분 충족** |
| 임베디드·HIL | 이산시간 모델, 상태·고장 분기, 신호 지연 일부 | 타깃 실행, 스케줄, 통신 스택, 계측/자극, HIL 입출력 | **미충족** |
| 차량 | 조립·실제 Rapier 움직임, 구동·제동·조향 관찰 | 타이어·현가·ABS/ESC 동작의 충실도와 측정 가능성 | **부분 충족** |

현재 블록 경험은 **주어진 입출력 사례를 만족하도록 기능 계산을 구성하는 연습**에는 유효하다. 모든 조건을 시스템적으로 찾아내거나 ECU 소프트웨어를 설계·검증하는 훈련으로는 부족하다. 모양 맞추기 퍼즐로 되돌리면 우연히 정답 그래프를 베끼는 문제가 생긴다. 각 후속 에피소드에 `관찰→동작 예측→직접 구성→정상·경계·고장 입력 선택→실패 신호 추적→수정`을 넣고, 같은 샘플의 블록 값·ECU 경계·장치 명령·차량 반응을 함께 재생해야 한다. 현재 최종 지도의 3D 하이라이트와 단계 재생은 **시간 동기화된 실제 실행 추적이 아니므로** 그 개발을 별도 완료 기준으로 둔다.

## 다음 구현 묶음과 완료 증거

1. 에피소드 1: READY 상태의 강제 주입을 없애고 START 이벤트, 프리차지 시간, 접촉기 장착·배선, BMS 사용 가능 신호를 주행 물리 게이트까지 하나로 연결한다. 정상·절연 오류·전압 부족을 플레이어 그래프로 시험한다.
2. 에피소드 2: 충전 포트·OBC·DC/DC·펌프·팬 3D 장치를 추가하고 SOC·온도·출력 제한을 동일 프레임으로 연결한다.
3. 에피소드 3~5: 회생·마찰 협조, 휠별 제동, EPS 보조 전류를 플레이어가 직접 만드는 별도 SWC/Runnable 미션으로 만들고 입력·출력·물리 명령을 동일 시간축에 기록한다.
4. 에피소드 6~7: 노면·현가와 E/E 신호·타임아웃·진단 미션을 만들고 다른 ECU 배치 옵션의 실제 저장/시험을 분리한다.
5. 실행 추적: 하나의 `tickId`, 입력·블록 중간값·ECU 송수신·액추에이터 명령·Rapier 결과를 기록하여 설계 지도와 3D에서 동일 이벤트로 재생한다.
6. 검수: 매 에피소드에 저장/복귀, 정상·경계·고장 시험, 그래프 오류, 부품 분리, 애니메이션/물리 일치, 키보드/모바일 화면 시험을 통과시킨다.

완료 판정은 문서·카드 또는 단일 틱 계산의 존재로 하지 않는다. **플레이어가 제작→검증→동일 차의 반응 확인→설계 지도 추적→저장 후 다음 에피소드**를 모두 수행할 때만 완료로 기록한다.
