# Vehicle Logic Lab — 차량 시스템 교육용 로직 퍼즐 게임 개발지시서

**문서 버전:** 2.0 (기존 1.0 대체)  
**개발 방식:** 기존 프로젝트 재사용 및 단계적 개편  
**주요 장르:** 차량 기능 조립형 퍼즐·시뮬레이션  
**첫 번째 학습 기능:** EV 구동 준비(READY) 상태 제어  
**확장 목표:** 차량의 모든 주요 기능 도메인과 다양한 검증 수준 지원  
**핵심 개발 원칙:** 교육적 이해도, 실제 작동하는 로직, 시각적 완성도, 재사용성, 점진적 개발

---

# 1. 개발 목표와 핵심 지시

기존 차량 고장 원인 추리 및 레이싱 게임 프로젝트를 바탕으로, 차량의 동작 원리를 직접 구성하고 검증하는 교육용 게임을 개발한다.

기존 프로젝트의 Canvas, 노드, 연결선, 차량 그래픽, 레이싱 기능, 추리 콘텐츠, 시스템 아키텍처 정보 및 각종 데이터를 가능한 범위에서 보존하고 재사용한다.

다만 게임의 주요 플레이 방식은 기존의 고장 추리에서 **차량 기능 로직 조립 퍼즐**로 변경한다.

플레이어는 차량이 정상적으로 동작하는 모습을 먼저 관찰하고, 주어진 입력·출력과 동작 조건에 맞춰 로직 블록을 연결한다.

완성한 로직을 시뮬레이션하면 차량 상태나 물리적 동작이 변화한다. 테스트를 통해 정상 동작이 확인되면 차량 기능이 완성되고 다음 콘텐츠가 해금된다.

**반드시 지켜야 할 사항**

- 기존 프로젝트 전체를 새로 작성하지 않는다.
- 기존 게임과 데이터는 확인 없이 삭제하지 않는다.
- 사용자가 실제로 체험할 수 있는 기능부터 완성한다.
- 검증되지 않은 자동차 기술 정보는 교육 콘텐츠로 확정하지 않는다.
- 구현이 어려운 기능을 가짜 데이터나 장식용 UI로 완성된 것처럼 표현하지 않는다.
- 한 번에 완성하기 어려운 기능은 `추가 예정`으로 명시하고 구현을 분리한다.
- 코딩 에이전트는 실제 구현 결과, 미구현 항목, 후속 작업을 구분해 보고한다.
- 플레이어에게 내부 데이터 구조와 개발용 식별자를 불필요하게 노출하지 않는다.

최종 지향점은 차량 구조를 암기하는 게임이 아니라, 차량 기능을 직접 만들고 시험하면서 차량 시스템을 이해하는 게임이다.

# 2. 최종 게임 콘셉트

## 2.1 게임의 정체성

**차량 기능을 하나씩 완성하여 나만의 차량 시스템을 구축하는 엔지니어링 퍼즐 게임**

플레이어는 개발 중인 가상의 EV를 맡은 엔지니어다.

처음 차량은 필수 기능 일부가 구현되지 않은 상태로 제공된다.

미션을 진행하면서 시동, 구동, 제동, 충전, 배터리 관리, 열관리 등의 기능을 완성한다.

각 기능을 완성하면 차량 시뮬레이터에서 그 결과를 확인할 수 있고, 검증에 통과한 기능은 차량에 적용된다.

게임은 단순히 블록 연결의 정답을 맞히는 것이 아니라, **실제 동작을 만들어내고 검증하는 경험**에 초점을 맞춘다.

## 2.2 핵심 플레이 흐름

1. 차량 기능의 정상 동작 관찰
2. 해당 기능의 원리와 목표 이해
3. 입력·출력 및 필요한 조건 확인
4. 로직 블록을 퍼즐 형태로 조립
5. 시뮬레이션 실행
6. 차량 상태·계기판·신호 변화 관찰
7. 다양한 조건에서 기능 검증
8. 테스트 실패 시 로직 수정
9. 검증 완료 후 차량 기능 활성화
10. 보상 및 다음 기능 해금

## 2.3 상태 머신과 로직 퍼즐의 관계

차량 상태 머신 게임을 별도로 만들지 않는다.

상태 머신은 기능 조립형 퍼즐에서 사용하는 로직 유형 중 하나로 취급한다.

따라서 게임은 다음을 모두 표현할 수 있어야 한다.

- 논리 조건
- 수치 연산
- 상태 전이
- 입력·출력 제어
- 제한 조건
- 시간 조건
- 인터페이스 처리
- 신호 유효성 검사

초기에는 Boolean 논리와 상태 전이만 구현하고 기능에 따라 차례로 확장한다.

# 3. 기존 레이싱 및 추리게임의 재활용

## 3.1 기본 원칙

기존 레이싱 게임과 추리게임은 폐기하지 않는다.

다만 새로운 학습 목적에 맞춰 역할을 변경한다.

**핵심 게임:** 로직 조립 퍼즐  
**응용 콘텐츠:** 테스트 트랙 및 문제 해결 챌린지

두 응용 콘텐츠는 독립적인 필수 학습 과정으로 강제하지 않는다.

로직 퍼즐만으로도 학습과 검증이 완결되어야 한다.

## 3.2 기존 레이싱 게임 → 테스트 트랙

기존 레이싱 게임은 **차량 제어 로직의 결과를 시각적으로 경험하는 공간**으로 재사용한다.

예시:

플레이어가 가속 토크 제어 기능을 완성한다.

해당 로직을 차량에 적용하면 테스트 트랙에서 가속 페달에 따라 차량이 움직인다.

이후 출력 제한 로직을 추가하면 같은 코스에서 가속 성능이 달라지는 것을 확인할 수 있다.

기능별 체험 예시:

| 학습 기능 | 테스트 트랙 활용 |
|---|---|
| READY 제어 | 구동 가능 상태 및 계기판 반응 |
| 가속 제어 | 페달 입력에 따른 가속 |
| 토크 제한 | 조건에 따른 출력 변화 |
| 제동 제어 | 감속 및 정지 |
| 회생제동 | 감속과 에너지 회수 |
| 열관리 | 온도 조건에 따른 출력 제한 |

**중요:** 플레이어가 만든 로직이 실제 테스트 트랙의 차량 동작에 반영되어야 한다.

단순히 퍼즐을 완료하면 기존 레이싱 게임이 해금되는 방식만으로는 교육적 연결성이 부족하다.

### 1차 개발 범위

기존 레이싱 게임의 소스와 에셋을 유지한다.

기존 레이싱 기능이 정상 작동한다면 이를 보존한다.

신규 로직과 실시간 연동하는 기능은 `추가 예정 — 테스트 트랙 통합`으로 관리한다.

단, 기존 차량 상태 표시나 계기판을 공통 시뮬레이션 화면에 쉽게 재사용할 수 있다면 우선 재사용한다.

로직 연동이 완성되지 않은 상태에서 실제 연동되는 것처럼 연출하지 않는다.

## 3.3 기존 고장 추리게임 → 문제 해결 챌린지

기존 추리게임은 후반 학습 및 응용 콘텐츠로 전환한다.

새로운 진행 방식:

1. 플레이어가 정상적인 차량 로직을 학습한다.
2. 로직을 완성하고 검증한다.
3. 이후 학습했던 기능에서 문제가 발생한다.
4. 플레이어는 기존에 학습한 원리를 이용해 원인을 확인한다.
5. 문제를 수정하거나 적절한 검증을 수행한다.

예시:

READY 상태 로직을 배운 후, 브레이크를 밟아도 READY가 활성화되지 않는 상황을 제시한다.

플레이어는 해당 기능을 이미 학습했으므로, 브레이크 입력·시스템 준비 조건·상태 전이 중 어느 부분을 확인할지 판단할 수 있다.

기존 추리게임처럼 처음부터 복잡한 ECU 구조와 로그를 모두 제공하지 않는다.

### 1차 개발 범위

기존 추리게임 코드와 데이터를 보존한다.

새 로직 퍼즐의 필수 진행 과정에서는 제외한다.

`추가 예정 — 문제 해결 챌린지`로 등록한다.

기존 추리 콘텐츠 중 검수되지 않은 내용은 정식 교육 미션에 사용하지 않는다.

## 3.4 메뉴 구성

권장 메인 메뉴:

- **차량 개발실** — 핵심 로직 퍼즐 게임
- **테스트 트랙** — 기존 레이싱 게임 활용
- **문제 해결 챌린지** — 기존 추리게임 활용
- **차량 시스템 지도** — 학습한 기능 확인

실제 작동 가능한 메뉴와 추가 예정 메뉴를 시각적으로 구분한다.

아직 연결되지 않은 콘텐츠는 비활성화하고 `추가 예정`이라고 표시한다.

단, 기존 레이싱 또는 추리게임이 이미 완성되어 정상 작동한다면 기존 실행 경로는 유지할 수 있다. 신규 기능과 연동되지 않았다는 점만 명확히 표시한다.

# 4. 게임의 재미와 보상 시스템

## 4.1 기본 설계 철학

플레이어가 퍼즐을 해결했을 때 단순한 PASS 메시지로 끝내지 않는다.

**기능을 완성했다는 성취감과 차량이 실제로 발전한다는 변화를 제공한다.**

다만 학습 목적과 관련 없는 복잡한 재화 시스템은 도입하지 않는다.

## 4.2 핵심 보상: 차량 기능 활성화

각 미션을 완료하면 차량의 특정 기능이 활성화된다.

예시:

- READY 기능 완성 → 차량 계기판 활성화
- 가속 기능 완성 → 차량 구동 체험 가능
- 제동 기능 완성 → 안전한 정지 동작 활성화
- 충전 기능 완성 → 충전 애니메이션 활성화
- 열관리 기능 완성 → 냉각 시스템 표시 활성화

활성화된 기능은 차량 시스템 지도에서 확인할 수 있다.

차량은 미션을 완료할수록 점진적으로 완성된다.

## 4.3 미션 완료 연출

미션을 완료하면 다음 효과를 제공한다.

- 성공한 로직의 신호 흐름 강조
- 기능 완성 애니메이션
- 차량 상태 변화
- 테스트 통과 결과
- 새롭게 학습한 핵심 개념 요약
- 다음 미션 해금

지나치게 긴 결과 화면이나 반복적인 축하 연출은 피한다.

권장 연출은 짧고 명확한 성공 애니메이션이다.

## 4.4 학습 기반 보상

정확한 검증을 수행하면 추가적인 성취감을 제공한다.

추천 보상:

**기능 완성**

필수 검증 통과 시 지급.

**정밀 검증**

경계 조건과 추가 테스트까지 통과했을 때 획득.

**설계 개선**

동일한 요구사항을 만족하면서 불필요한 블록을 줄이거나 로직을 단순화했을 때 획득.

설계 개선 평가는 기능 정확성 검증 이후에만 진행한다.

블록 수가 적다는 이유만으로 안전하지 않은 설계를 높은 점수로 평가해서는 안 된다.

## 4.5 별점·점수 시스템

1차 버전에서는 단순한 3단계 평가를 사용한다.

- 1단계: 필수 로직 정상 동작
- 2단계: 필수 테스트 모두 통과
- 3단계: 추가 조건 또는 도전 테스트까지 통과

힌트를 사용해도 미션 완료는 가능해야 한다.

힌트 사용에 큰 불이익을 주지 않는다.

교육용 게임이므로 정답을 빠르게 맞히는 것보다 원리를 이해하고 검증하는 것을 우선한다.

## 4.6 추가 예정 보상

- 차량 외관 커스터마이징
- 테스트 트랙별 기록
- 새로운 검증 환경 해금
- 도전 과제
- 고급 엔지니어링 배지

초기에는 보상 시스템을 과도하게 확장하지 않는다.

# 5. 차량 아키텍처와 교육 설계

## 5.1 핵심 학습 관점

본 게임의 중심은 기능 아키텍처다.

플레이어가 차량 기능을 학습하면서 E/E, SW, 물리 구조 및 검증 개념을 자연스럽게 이해하도록 한다.

## 5.2 아키텍처 구분

| 관점 | 의미 | 게임에서의 역할 |
|---|---|---|
| 기능 아키텍처 | 무엇을 수행하는가 | 핵심 학습 대상 |
| 시스템 아키텍처 | 어떤 시스템들이 협력하는가 | 기능 관계 설명 |
| E/E 아키텍처 | ECU·센서·네트워크·전원이 어떻게 구성되는가 | 구현 관계 설명 |
| SW 아키텍처 | 어떤 로직과 소프트웨어로 구현되는가 | 퍼즐 및 로직 학습 |
| 물리 아키텍처 | 실제 장치가 어떻게 구성되고 동작하는가 | 차량 시각화 |
| 검증 관점 | 무엇을 어떤 수준에서 확인하는가 | 미션 난도와 검증 |

서로 다른 아키텍처 관점을 하나의 고정된 상하 계층으로 표현하지 않는다.

예를 들어 구동 기능이 복수 ECU에 분산될 수 있고, 하나의 ECU에 여러 도메인의 기능이 할당될 수 있다.

## 5.3 E/E와 기능 도메인의 구분

기능 도메인은 차량의 수행 목적을 기준으로 나눈다.

E/E 아키텍처는 기능을 구현하는 전기·전자 구조를 의미하며 논리적인 제어기 관계와 물리적인 배선·배치 관계를 모두 포함한다.

게임은 기능 이해를 먼저 제공하고, 이후 실제 구현과 관련된 ECU와 통신 정보를 연결해 보여준다.

## 5.4 검증 수준

게임에서 다음 검증 범위를 지원할 수 있도록 설계한다.

- Unit
- Component
- Integration
- System
- Vehicle

MIL, SIL, PIL, HIL은 검증 환경을 나타내므로 위 검증 범위와 동일한 레벨로 취급하지 않는다.

실제 하드웨어가 없는 교육용 시뮬레이션을 HIL로 표시하지 않는다.

## 5.5 플레이어 정보 노출 원칙

플레이어가 차량 기능을 이해하는 데 필요한 정보만 기본 화면에 제공한다.

처음부터 ECU 전체 목록, CAN ID, 복잡한 신호 정의, 전체 요구사항 데이터베이스를 보여주지 않는다.

학습 흐름:

- 처음: 이 기능이 무엇을 하는가?
- 로직 조립: 어떤 입력과 조건으로 동작하는가?
- 검증: 어떤 상황에서 정상적으로 동작해야 하는가?
- 심화: 실제 차량에서는 어떤 ECU와 인터페이스가 관계되는가?

전문 정보를 숨기거나 삭제하는 것이 아니라 학습 단계에 따라 제공한다.

실제 개발을 시작하기 전에 기존 코드와 자산을 조사한다.

확인 대상:

- Canvas 구현
- 노드 및 연결선 시스템
- 입력 이벤트 처리
- 상태 관리
- 그래픽 엔진
- 차량 시뮬레이션

- 기존 추리 시스템
- 요구사항 데이터
- 신호 정의

- 아키텍처 정보
- 테스트 시스템

- 기존 저장 데이터

## 6.2 재사용 판정

- 그대로 사용

## 6.3 기존 구현 보호

기존 시스템을 일괄 삭제하지 않는다.

기존 레이싱과 추리게임을 새 메인 게임에서 사용하지 않더라도 소스 및 자산을 보존한다.

가능하면 기존 기능을 별도 라우트나 모듈로 분리한다.

기존 데이터를 신규 형식으로 이전할 경우 원본을 보존하고 변환된 데이터를 별도로 관리한다.

기존 프로젝트가 정상 작동하는 기준 상태를 먼저 확보하여 이후 회귀 문제를 확인할 수 있도록 한다.

# 7. 기존 요구사항·신호·인터페이스·아키텍처 데이터 관리

## 7.1 기본 원칙

기존 자료를 모두 버리지 않는다.

다만 내용 검수가 완료되지 않았으므로 정답 데이터로 무조건 신뢰하지 않는다.

자료를 다음 세 가지로 분류한다.

**검수 완료**

교육용 콘텐츠에 사용 가능.

**검수 대기**

원본은 보존하지만 정식 미션·채점에는 사용하지 않음.

**사용 부적합**

오류, 중복, 모순 또는 불명확한 출처가 확인되어 정식 콘텐츠에서 제외.

## 7.2 검수 기준

자료별로 다음을 확인한다.

- 기능 정의가 적절한가?
- 실제 차량의 일반적인 원리와 일치하는가?
- 특정 제조사 또는 차종에만 해당하는 내용인가?
- 입력과 출력의 의미가 명확한가?
- 신호 단위와 유효 범위가 타당한가?
- 인터페이스 방향이 적절한가?
- 요구사항이 검증 가능한 형태인가?
- 모순되는 조건이 존재하는가?
- 교육용으로 단순화한 부분이 명확한가?
- 참고 근거 또는 적용 전제가 있는가?

## 7.3 기존 데이터의 재사용 방식

| 기존 데이터 | 신규 활용 |
|---|---|
| 요구사항 | 미션 목표 및 검증 조건 |
| 인터페이스 | 기능 간 연결 관계 |
| 신호 | 퍼즐 입력·출력 |
| ECU 정보 | E/E 아키텍처 설명 |
| 시스템 구조 | 차량 시스템 지도 |
| 정상 동작 시나리오 | 튜토리얼 및 테스트 |
| 고장 시나리오 | 추후 문제 해결 챌린지 |
| 로그 | 신호 모니터 및 분석 화면 |

## 7.4 검수 전 자료의 처리

검수되지 않은 자료를 게임 내부 정답이나 테스트 기대값으로 직접 사용하지 않는다.

실제 차량 지식이라고 단정할 수 없는 내용은 교육용 가상 차량 사양으로 구분한다.

게임의 초기 READY 기능은 명시적인 가상 차량 요구사항을 기준으로 작성하고, 해당 요구사항과 테스트를 함께 검토한다.

## 7.5 개발자용 검수 보고서

개발 과정에서 다음 항목을 보고한다.

- 재사용 가능한 기존 데이터
- 검수가 필요한 데이터
- 불일치 또는 오류 의심 사항
- 근거가 부족한 내용
- 데이터 정리 후 활용 가능한 기능
- 신규 콘텐츠로 활용하기 좋은 자료

자료가 방대하다면 첫 개발 단계에서는 목록화와 분류까지만 진행한다.

전체 내용 검수를 완료하지 못한 상태에서는 `추가 예정 — 기존 차량 데이터 검수`로 남긴다.

**데이터가 존재한다는 이유만으로 게임에 억지로 노출하지 않는다.**

# 8. 시스템 전체 아키텍처

## 8.1 구조적 목표

차량 도메인과 게임 엔진을 분리한다.

새로운 차량 기능을 추가할 때 기존 Canvas, 로직 엔진, 검증 엔진을 매번 수정하지 않도록 한다.

## 8.2 핵심 모듈

**미션 관리자**

미션 선택, 진행 및 완료 처리.

**Canvas 편집기**

블록 배치, 연결, 편집.

**블록 레지스트리**

사용 가능한 연산 및 제어 블록 관리.

**로직 실행 엔진**

블록 그래프 평가 및 상태 전이 실행.

**시뮬레이션 엔진**

시간, 입력 변화, 시스템 상태 관리.

**검증 엔진**

테스트 실행 및 결과 비교.

**시각화 관리자**

로직 실행 결과를 그래픽으로 표현.

**학습 콘텐츠 관리자**

기능, 요구사항, 학습 설명 및 테스트 정의.

**차량 시스템 지도**

학습한 기능과 관련 아키텍처 표시.

**진행·보상 관리자**

해금, 성취도 및 저장 데이터 관리.

**기존 게임 어댑터**

레이싱과 추리 콘텐츠 연결을 위한 확장 지점.

## 8.3 시스템 연결 원칙

```text
학습 콘텐츠 / 미션
        ↓
   Canvas 로직 편집
        ↓
     로직 엔진
        ↓
   시뮬레이션 실행
        ↓
  ┌─────────────┐
  │             │
검증 엔진     시각화 엔진
  │             │
  └──────┬──────┘
         ↓
   결과 / 보상 / 해금
         ↓
차량 시스템 지도에 반영
```

기존 레이싱과 추리게임은 공통 시뮬레이션 또는 콘텐츠 인터페이스를 통해 추후 연결한다.

현재 구현되지 않은 연결은 빈 함수나 가짜 성공 결과로 처리하지 않는다.

명시적인 미구현 상태를 반환하거나 기능 자체를 비활성화한다.

## 8.4 범용성 요구사항

새로운 기능을 추가할 때 다음 데이터만 준비하면 기존 시스템에서 미션을 생성할 수 있도록 한다.

- 기능 정의
- 학습 목표
- 입출력
- 사용 가능한 블록
- 초기 그래프
- 요구사항
- 테스트 시나리오
- 시각화 설정
- 완료 보상

새로운 종류의 연산이나 물리 모델이 필요할 때만 공통 플러그인 인터페이스를 확장한다.

모든 차량 기능을 기존 Boolean 블록에 억지로 맞추지 않는다.

# 9. 내부 식별자와 플레이어 표시 정보의 분리

## 9.1 최우선 UI 원칙

**개발용 식별자는 기본적으로 플레이어에게 노출하지 않는다.**

프로그램 내부에서 ID가 필요한 것은 정상이다.

하지만 ID는 데이터 연결, 저장, 참조를 위해 존재하는 기술적 요소이며 학습 콘텐츠가 아니다.

기본 화면에서는 사람에게 이해하기 쉬운 이름과 설명을 우선한다.

## 9.2 표시 예시

| 내부 데이터 | 플레이어 표시 |
|---|---|
| `REQ-READY-001` | 시동 조건 확인 |
| `Brake_Pressed` | 브레이크 페달 |
| `System_OK` | 시스템 준비 완료 |
| `TC-READY-03` | 브레이크를 밟지 않고 시동 걸기 |
| `Drive_Enable` | 구동 허용 |
| `State_Transition` | 상태 전환 |
| `CAN_TIMEOUT` | 제어 정보가 도착하지 않음 |

실제 코딩을 위해 내부 식별자를 사용하는 것은 허용한다.

다만 화면 상단에 `REQ`, `TC`, `ECU`, `ID`가 반복 표시되는 구성은 피한다.

## 9.3 정보 공개 수준

**기본 모드**

- 친숙한 한글 명칭
- 짧은 기능 설명
- 직관적인 입출력
- 필요한 동작 조건
- 시뮬레이션 결과

**상세 설명**

- 실제 기술 용어
- 신호 이름
- 관련 ECU
- 인터페이스 관계
- 아키텍처 위치

**개발자/고급 정보**

- 내부 ID
- 원시 데이터
- 신호 타입
- 정확한 타이밍
- 요구사항 추적성
- 테스트 세부 로그

상세 정보는 필요한 경우에만 펼칠 수 있도록 한다.

단, 전문 용어를 무조건 제거하지는 않는다.

READY, BMS, VCU, CAN 등 학습해야 할 용어는 먼저 한글로 설명한 후 실제 명칭을 함께 제공한다.

- 출력 변경 애니메이션
- 실패 조건 강조

과도한 발광이나 애니메이션으로 가독성을 떨어뜨리지 않는다.

# 11. 차량 시뮬레이션과 그래픽

## 11.1 그래픽 제작의 목적

차량 그래픽은 단순한 장식이 아니다.

플레이어가 만든 로직이 차량에 어떤 영향을 주는지 설명하는 교육 도구다.

따라서 시뮬레이션과 그래픽은 반드시 연동되어야 한다.

## 11.2 화면 구성

**상단**

현재 미션과 동작 목표.

**좌측**

로직 블록 목록 및 간단한 힌트.

**중앙**

로직 Canvas.

**우측**

차량 또는 관련 구성요소의 시각화.

**하단**

입력 조작, 실행, 테스트 결과 및 신호 변화.

Canvas와 차량 시각화를 동시에 볼 수 있어야 한다.

## 11.3 차량 시각화 종류

기능에 따라 서로 다른 시각화 방식을 사용한다.

**차량 상태 화면**

READY, OFF, 경고등 등의 상태 표시.

**차량 동작 화면**

가속, 감속, 정지 등 물리적 변화.

**구성요소 화면**

배터리, 모터, 인버터, 냉각 시스템 등.

**에너지·신호 흐름**

전력 흐름, 통신 신호, 제어 명령.

**계기판**

속도, 출력, SOC, 상태 표시 등.

하나의 기능에 필요한 시각화만 표시한다.

## 11.4 그래픽 스타일

목표 스타일은 고품질 엔지니어링 게임 UI다.

권장 방향:

- 정돈된 다크 테마
- 전문적인 차량 개발실 분위기
- 고해상도 차량 그래픽
- 부드러운 상태 변화
- 명확한 계기판
- 자연스러운 Canvas 애니메이션
- 통일된 색상과 아이콘
- 적절한 깊이감과 조명 효과

그래픽은 시뮬레이션 및 학습 결과를 명확하게 전달해야 한다.

## 11.5 기존 그래픽 우선 활용

다음 순서로 검토한다.

1. 기존 프로젝트 차량 그래픽
2. 기존 레이싱 게임의 차량 모델
3. 기존 UI와 애니메이션 자산
4. 기존 아이콘 및 SVG
5. 새로운 그래픽 제작

기존 그래픽이 품질 기준을 충족하지 못하는 경우에는 개선 대상으로 분류한다.

## 11.6 그래픽 제작 분리 원칙

한 번의 코딩 요청으로 차량 모델, 애니메이션, 물리 시뮬레이션, 아키텍처 도면을 모두 완성하려 하지 않는다.

고품질 그래픽을 제작하기 어렵다면 다음과 같이 분리한다.

**현재 구현**

- 기본 Canvas 디자인
- 차량 상태를 보여주는 실사용 가능한 계기판
- 상태 변화 애니메이션
- 입력에 따른 신호 하이라이트

**추가 예정**

- 고품질 3D 차량
- 배터리 단면 애니메이션
- 모터 구동 애니메이션
- 열관리 유체 흐름
- ECU 및 하네스 구조 시각화
- 차량 전체 에너지 흐름

## 11.7 미완성 그래픽 표시 규칙

기능이 완성되지 않았다면 억지로 저품질 그림을 생성하지 않는다.

대신 다음 조건을 만족하는 스텁을 둔다.

- 어떤 그래픽이 들어갈지 명확하게 설명
- 현재 구현 상태 표시
- 필요한 입력 신호 지정
- 출력 애니메이션 요구사항 기록
- 추후 제작 작업으로 분류

예시:

`추가 예정 — EV 배터리 냉각 시스템 시각화`

단, 첫 번째 READY 미션의 계기판과 상태 전환처럼 핵심 플레이에 필수적인 그래픽은 실제로 구현해야 한다.

핵심 기능까지 추가 예정으로 처리해서는 안 된다.

# 12. 첫 번째 콘텐츠: EV 구동 준비 상태

## 12.1 학습 목적

EV에서 구동 가능한 상태가 어떤 입력 및 조건에 따라 결정되는지 이해한다.

초기 기능은 READY 상태 제어로 제한한다.

차량 제조사마다 구체적인 제어 조건이 다를 수 있으므로 본 게임에서는 가상의 교육용 차량 사양을 사용한다.

## 12.2 상태 정의

**전원 꺼짐 (OFF)**

차량 제어 전원 비활성 상태.

**시동 대기 (STANDBY)**

일부 제어 기능은 활성화되었으나 구동이 허용되지 않은 상태.

**주행 준비 완료 (READY)**

구동 가능 조건을 만족한 상태.

READY는 실제 차량이 움직이고 있다는 뜻이 아니다.

## 12.3 플레이어 입력

- 전원 버튼
- 브레이크 페달
- 시스템 준비 상태
- 차량 정지 여부

## 12.4 플레이어 출력

- 현재 차량 상태
- READY 표시
- 구동 허용 여부

실제 차량 신호명은 상세 정보에서만 표시한다.

## 12.5 미션 1 — 시동 조건 만들기

**플레이어에게 보여줄 설명**

"브레이크를 밟고 시스템 준비가 완료된 상태에서 시동 버튼을 누르면 차량이 주행 준비 상태가 되도록 만드세요."

초기 상태는 시동 대기 상태로 설정한다.

플레이어는 필요한 논리 블록을 연결한다.

정상 조건이 충족되면 READY 진입 요청이 활성화된다.

입력 중 하나라도 조건을 만족하지 못하면 요청이 활성화되지 않는다.

**중요한 구현 규칙**

첫 번째 미션에서는 READY 진입 조건의 참·거짓을 계산한다.

실제 상태 변경은 미션 2의 상태 머신으로 수행한다.

미션 1의 출력이 참이라는 이유만으로 내부 차량 상태를 즉시 READY로 변경하지 않는다.

다만 목표 동작을 설명하기 위한 미리보기 애니메이션은 사용할 수 있다.

## 12.6 미션 2 — 차량 상태 연결하기

플레이어는 세 가지 차량 상태와 전이 조건을 연결한다.

기본 전이:

- OFF → STANDBY
- STANDBY → READY
- READY → OFF

상태 전이는 전원 버튼 이벤트, 브레이크 조건, 시스템 준비 상태 및 차량 정지 여부에 따라 결정한다.

전원 버튼 이벤트는 발생 순간에만 처리하며, 버튼을 계속 누르고 있다는 이유로 여러 상태를 연속 통과해서는 안 된다.

플레이어는 현재 상태에 따라 같은 버튼 입력도 다른 결과가 발생할 수 있음을 학습한다.

## 12.7 미션 3 — 다양한 시동 조건 시험하기

플레이어는 정상·비정상 조건을 테스트한다.

권장 테스트:

- 정상 시동
- 브레이크 미입력
- 시스템 준비 미완료
- 차량 정지 상태에서 전원 종료
- 차량 정지 조건 미충족 시 전원 종료 요청
- 이벤트가 없을 때 상태 유지

**플레이어 표시 예시**

- 정상적으로 시동 걸기
- 브레이크 없이 시동 걸기
- 시스템이 준비되지 않았을 때 시동 걸기
- 정차 후 전원 끄기

테스트의 내부 식별자는 기본 화면에 표시하지 않는다.

정상 결과와 실제 결과를 비교하고, 실패 시 관련 로직을 강조한다.

## 12.8 READY 미션의 그래픽

최소한 다음은 실제 구현한다.

- 차량 또는 계기판 그래픽
- 현재 상태 표시
- 전원 버튼 인터랙션
- 브레이크 입력 표시
- READY 활성화 애니메이션
- 로직 활성 경로 표시
- 성공 및 실패 피드백

미션 완료 시 READY 기능이 차량 시스템 지도에서 활성화된다.

# 13. 시뮬레이션 및 검증 엔진

## 13.1 시뮬레이션

블록 연결로 구성한 로직은 실제로 실행한다.

시뮬레이션 엔진은 입력, 현재 상태, 이벤트를 기반으로 출력을 계산한다.

초기 실행은 결정론적이어야 한다.

동일한 초기 상태와 입력 시퀀스에서는 같은 결과가 나와야 한다.

## 13.2 테스트 검증

테스트는 다음 항목으로 구성한다.

- 초기 상태
- 입력 조건
- 입력 이벤트
- 기대 상태
- 기대 출력
- 판정 결과

단순히 정답 그림과 일치하는지 확인하지 않는다.

## 13.3 실패 피드백

예를 들어 브레이크를 밟지 않았는데 READY 조건이 활성화되었다면:

"브레이크를 밟지 않았는데 시동 허용 조건이 활성화됐습니다. 브레이크 입력이 판단 조건에 포함되었는지 확인하세요."

이와 같이 플레이어가 이해할 수 있는 설명을 표시한다.

상세 정보에서는 입력 신호와 계산 결과를 보여줄 수 있다.

## 13.4 검증 난도 확장

초급:

- Boolean 조건
- 정상 시나리오
- 상태 전이

중급:

- 수치 제한
- 경계 조건
- 복수 기능 연결

고급:

- 인터페이스
- 신호 유효성
- 타이밍 및 Timeout

심화:

- 고장 주입
- 시스템 통합
- 회귀 테스트

실제 구현은 초기 수준으로 제한한다.

# 14. 차량 시스템 지도

## 14.1 목적

플레이어가 완성한 기능이 차량 전체에서 어떤 역할을 수행하는지 확인하는 화면이다.

## 14.2 기본 표현

차량을 중심으로 주요 기능 도메인을 보여준다.

예시:

- 구동
- 배터리
- 충전
- 제동
- 조향
- 열관리
- 차체
- ADAS
- 진단

기능을 완료하면 해당 항목이 활성화된다.

완료하지 않은 기능은 잠금 또는 추가 예정 상태로 표현한다.

## 14.3 상세 정보

기능을 선택하면 다음을 보여준다.

- 기능 설명
- 정상 동작 원리
- 관련 입력·출력
- 관련 시스템
- 완료한 미션
- 검증 결과

E/E 및 SW 상세 구조는 추후 추가한다.

## 14.4 기존 아키텍처 데이터 활용

기존 아키텍처 데이터는 검수 상태에 따라 단계적으로 표시한다.

검수되지 않은 복잡한 구조를 첫 화면에 대량으로 표시하지 않는다.

아키텍처 정보를 많이 보여주는 것이 교육적 완성도를 의미하지는 않는다.

## 15.4 범용성 확인

READY 기능과 다른 도메인의 간단한 기능을 하나 등록하여 공통 시스템의 재사용성을 확인한다.

권장 내부 테스트는 도어 잠금 조건이다.

도어 잠금 샘플은 정식 콘텐츠로 공개할 필요가 없다.

# 16. 게임 UI 및 사용성

## 16.1 기본 원칙

플레이어에게는 기술 자료가 아니라 게임을 하고 있다는 인상을 제공해야 한다.

다음 요소를 우선한다.

- 명확한 목표
- 직관적인 입력
- 시각적인 로직 구성
- 즉각적인 출력 피드백
- 차량 동작의 변화
- 짧고 이해하기 쉬운 설명
- 단계적 힌트

## 16.2 정보량 제한

초급 미션에서는 현재 문제와 관련이 없는 신호나 ECU를 표시하지 않는다.

기술적 세부사항은 상세 정보에서 확인하도록 한다.

개발용 식별자, 내부 데이터 구조, 긴 JSON 문서 등을 플레이어 화면에 직접 표시하지 않는다.

## 16.3 용어 처리

처음 등장하는 전문 용어에는 간단한 설명을 제공한다.

예:

**READY**

"차량이 주행할 수 있도록 구동 준비가 완료된 상태"

**상태 전이**

"특정 조건에 따라 차량의 동작 상태가 다른 상태로 바뀌는 것"

**입력 신호**

"제어 로직이 판단에 사용하는 정보"

## 16.4 힌트 제공

1단계: 기능 원리 설명

2단계: 필요한 입력 조건 설명

3단계: 필요한 블록 제안

4단계: 연결 관계 예시

힌트 사용 여부와 관계없이 학습을 완료할 수 있어야 한다.

# 17. 추가 예정 및 스텁 관리 규칙

## 17.1 목적

한 번의 개발 요청에서 구현 가능한 범위를 초과하는 기능을 억지로 완성하지 않기 위한 규칙이다.

**핵심 기능은 완성하고, 부가 기능은 명확하게 보류한다.**

## 17.2 스텁 허용 대상

다음은 추가 예정으로 남길 수 있다.

- 3D 차량 뷰어
- 물리 기반 레이싱 연동
- 고급 고장 분석
- 차량 전체 아키텍처 그래픽
- 상세 E/E 네트워크 시각화
- 고급 신호 그래프
- 고급 보상·커스터마이징
- 검수되지 않은 차량 도메인 콘텐츠

## 17.3 스텁 금지 대상

다음 핵심 기능은 가짜 구현으로 대체하지 않는다.

- 로직 블록 연결
- 기본 그래프 실행
- 기본 상태 전이
- 필수 테스트 실행
- 기대 결과와 실제 결과 비교
- READY 기능의 상태 시각화
- 미션 완료 판정

## 17.4 스텁 표시 형식

화면에 노출되는 스텁:

`추가 예정 — [기능 이름]`

개발 문서의 스텁:

- 기능 이름
- 구현 목적
- 현재 상태
- 필요한 데이터
- 기존 재사용 가능 요소
- 구현 시 주의사항
- 후속 개발 지시

구현되지 않은 버튼을 눌렀을 때 정상 완료 메시지를 출력하지 않는다.

동작하지 않는 기능을 실제 작동하는 것처럼 묘사하지 않는다.

## 17.5 추가 개발 프롬프트 생성

코딩 에이전트는 구현을 마친 뒤, 남아 있는 추가 예정 항목에 대한 후속 작업 프롬프트를 작성한다.

각 프롬프트는 별도의 작업으로 실행 가능해야 한다.

예:

**후속 작업 A — 테스트 트랙 연동**

"기존 레이싱 게임을 재사용하여 로직 시뮬레이션의 구동 명령이 차량 움직임에 반영되도록 연결하라. 기존 레이싱 코드와 물리 로직을 먼저 분석하고 가능한 기능을 재사용할 것."

**후속 작업 B — 그래픽 고도화**

"현재 완성된 READY 로직 시뮬레이션에 고품질 계기판과 차량 상태 애니메이션을 추가하라. 실제 시뮬레이션 상태와 동기화할 것."

**후속 작업 C — 기존 자료 검수**

"기존 요구사항, 신호, 인터페이스 및 아키텍처 데이터를 분류하고 오류 및 불명확한 내용을 검토하라. 검수 완료된 자료만 신규 학습 콘텐츠에 연결할 것."

후속 작업은 우선순위와 의존 관계도 함께 설명한다.

# 19. 완료 기준

## 19.1 기본 플레이

플레이어가 게임에 진입해 READY 기능을 선택하고, 로직을 직접 연결하여 정상적으로 실행할 수 있어야 한다.

입력 조건을 변경하면 출력과 상태가 실제 계산 결과에 따라 변경되어야 한다.

## 19.2 검증

잘못된 로직을 구성하면 테스트가 실패해야 한다.

로직을 수정하여 요구사항을 충족하면 테스트를 통과해야 한다.

## 19.3 시각화

차량 계기판과 상태 그래픽이 실제 시뮬레이션 결과와 일치해야 한다.

## 19.4 보상

미션 완료 시 기능 완성 연출이 제공되고 차량 시스템 지도에 진행 결과가 반영되어야 한다.

## 19.5 기존 프로젝트 보존

기존 레이싱 및 추리게임 코드와 데이터가 의도하지 않게 손상되거나 삭제되지 않아야 한다.

## 19.6 범용성

새로운 기능을 등록할 때 공통 게임 엔진을 재작성하지 않아야 한다.

## 19.7 미완성 기능

구현되지 않은 항목은 모두 추가 예정으로 분류되어야 한다.

실제 구현된 기능과 미구현 기능의 구분이 명확해야 한다.

# 21. 최종 개발 지시

기존 프로젝트를 기반으로 차량 기능 로직 조립형 교육 게임을 구현하라.

게임의 핵심은 정상 동작을 관찰하고 입력·출력 조건에 따라 로직을 구성한 뒤, 실제 실행과 테스트를 통해 차량 동작을 검증하는 것이다.

기존 Canvas 및 그래픽 자산을 최대한 재사용하고, 기존 레이싱 게임은 추후 테스트 트랙으로, 고장 추리게임은 추후 문제 해결 챌린지로 활용할 수 있도록 보존하라.

차량 도메인 정보와 게임 엔진을 분리하여 새로운 차량 기능을 콘텐츠 단위로 추가할 수 있게 설계하라.

현재 구현 범위는 EV READY 상태 제어의 3개 미션으로 제한한다.

플레이어에게는 기술 데이터베이스가 아닌 직관적인 학습 게임을 제공해야 한다. 내부 ID와 복잡한 아키텍처 정보는 필요할 때만 상세 화면에서 제공한다.

기존 요구사항, 신호, 인터페이스 및 아키텍처 자료는 폐기하지 말고 검수 상태에 따라 관리하라. 검수되지 않은 내용을 게임 정답이나 실제 차량의 사실로 사용하지 말라.

그래픽은 교육을 위한 핵심 요소로 취급한다. 로직, 신호, 차량 상태가 실제로 연동되는 고품질 시각화를 구현하되, 한 번에 완성하기 어려운 부가 그래픽은 추가 예정으로 분리한다.

핵심 기능을 가짜 구현이나 장식용 데모로 대체하지 말라.

**첫 번째 목표는 단순한 기능 소개 화면이 아니라, 플레이어가 실제로 로직을 조립하고 차량의 상태 변화를 확인하며 검증에 성공할 수 있는 완성된 게임 경험이다.**

개발 종료 시 실제 완성 항목, 재사용 자산, 검수 대기 자료, 추가 예정 기능 및 후속 개발 프롬프트를 반드시 보고하라.
