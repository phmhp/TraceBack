# v0.14.0 — 도메인 조립과 설계/실행 분리

## 왜 첨부 화면에서 막혔나

v0.13의 정상 관찰 화면은 제공 모델 시연, 자유 입력, 제어기 상태, 다음 SW 작업을 한 화면에 겹쳐 보여 줬다. 페달 조작이 ‘전력 경로를 배우는 행동’인지 ‘내 퍼즐의 검증’인지 불명확했다. 부품 수만 늘리면서 개별 장착 반복도 늘었다. 이는 자동차 공부가 본래 어렵기 때문만이 아니라 화면의 활동 구분과 다음 행동 안내가 부족했던 문제다.

이번 흐름은 다음과 같다.

**구매 애니메이션 → 한 곳의 운전자 입력 → 도로 위 사건 → 도메인 수첩 → 기능 묶음 조립/도식 누적 → 제공 정상 동작 시범 → 설계도 보며 SW 퍼즐 → 실행 탭의 준비된 상황 → 통합 확인 → 같은 설계로 대회.**

## 요청별 반영

| 요청 | 구현 |
|---|---|
| 영화의 현실적인 촬영 분위기 | 자체 레이싱 단편을 낮은 트랙/측면/추적의 네 컷, 낮은 프로토타입 차량·스트라이프·방호벽으로 재구성. TV 렌더 타깃 640×360→1280×720. 공식 영화 자료는 참고 출처이며 스틸·원본 영상·로고·음악은 패키지에 넣지 않음 |
| 고양이 눈 깨짐 | 머리 표면에서 눈을 분리하고 고밀도 구형 눈·비조명 눈동자·작은 하이라이트 사용. 원래 모모의 정체성과 짧은 몸 비율 유지 |
| 구매도 애니메이션 | 구매 전 시장, 고양이 보행, 열쇠 전달, 차량 인수 후 출발. 인수 완료에만 구매 거래/시운전 진행 |
| 차가 조잡하고 그림자 없음 | 빨간 곡면 소형차·크림 루프·원형 전조등·휀더·창·트림. 접지 그림자와 이동 차량을 따라오는 실제 광원 그림자, 도로 receiveShadow. 상대 차는 절제한 청회색/보라/민트색 |
| 운전석이 너무 가까움 | 뒤로 물린 카메라와 더 넓은 하부 시야, 고양이 손의 핸들 림 접촉/조향/기어 요청 이동, 페달과 발 동작, 기어 레버 움직임. 부품/차량 반응은 현재 입력을 사용 |
| 와르르가 정비소 폭발처럼 보임 | 사건에도 도로와 차량의 실제 위치 유지, 외장/바퀴 이완 연출, 옆 차의 추월. 다음 선택에서 정비소 조사로 전환. 이는 스토리 연출이며 실제 고장 원인/파손 해석이 아님 |
| 시운전 조작 중복 | 차량 아래 중복 조작계/HUD/설명을 제거하고 오른쪽 START·PRND·브레이크·가속과 상태 도식에 통합. 방향키/실제 운전석 조작은 유지 |
| 도메인·차량 전체 위치 | 차량 스케치 수첩에서 구동·전력·입력/ECU·제동·조향·기본 현가 위치와 현재 영역 표시. 기계/에너지, E/E, SW 관점 전환. 차고 설계도도 같은 수첩 사용 |
| 입력/출력·ECU 구분 | 입력→제어/전달→출력/반응 구분. 전력 공급 경로는 센서 신호와 분리. ECU가 모터/브레이크/조향 기구를 없애는 것으로 설명하지 않음 |
| 조립 클릭 반복 | 동일 15종 실제 기록을 회전 전달·네 바퀴·전력·입력/ECU·제동·조향 6묶음으로 구성. 묶음을 한 번 시작하면 부품별 운반/고정/배선을 연속 실행. 네 바퀴는 한 번 시작으로 4개 기록을 각각 장착 |
| 조립과 도식의 누적 | KitFlow가 부품별 실제 FIXED 상태에 따라 추가·체크·연결됨. 전체 수첩의 장착 상태도 같은 기록 사용. 바퀴 4개 도식은 에너지 직렬 연결이 아니라 장착 순서임을 표시 |
| 정상 관찰 화면이 모호함 | 복잡한 자유 슬라이더를 없애고 전력/입력과 ECU/제동의 정상 시범 버튼 및 실제 출력으로 구성. 이후 만드는 SW의 자리를 설명 |
| Simulink 느낌은 유지하되 쉽게 | 큰 기능→내부 연산은 유지. 기본은 쉬운 블록 이름·연결됨 표시, 전문 블록명/수치는 선택. 허용 조건은 기어 판단→제동 판단→AND 결과 전달의 작은 퍼즐로 나눔. 전체 연결은 선택 |
| 오른쪽 설계도 참고 / 실행 탭 | ① 설계: 왼쪽 퍼즐, 오른쪽 동작 설계 참고도와 요구사항 상세. ② 실행: 정해진 상황 카드, 내 실제 출력, 독립 기대값 일치/불일치와 차량. 기본 퍼즐에 자유 A/B·기어·센서 슬라이더 없음 |
| 다음 행동이 안 보임 | 상단 입력 연결 수와 ‘연결 후 동작 확인’, 조건별 다음 연결 버튼, 실행 후 ‘확인 완료·다음 기능’. 5회 실패 튜토리얼/실제 한 연결 시범 유지. 단계 사이 강제 지도 모달 제거 |

## 아키텍처를 나눈 기준

도메인은 차가 하는 일이고, 아래 관점은 그 일을 어떻게 구현하는지 보는 방법이다. 하나의 일률적 상하 계층으로 주장하지 않는다.

- **기계·에너지:** 배터리 전력, 모터 회전, 감속/동력 전달, 브레이크, 조향 기구, 타이어/현가.
- **E/E:** 센서·ECU·전원·액추에이터 연결과 기능 배치. 이 게임에서는 추상화한 신호 연결을 사용하며 CAN 프레임/전력 회로 정밀 모델은 아님.
- **SW:** 해당 ECU 안의 요청 계산/조건 판단/명령 출력. 직접 설계·검증하는 범위는 VCU 전진 구동이다.

ECU가 기계 장치를 대체하는 것이 아니다. SW가 명령을 계산하고 인버터·액추에이터가 에너지를 힘으로 바꾸며 기구가 전달한다. 수동 현가는 ECU 없이도 동작한다. PRND 요청은 기어/구동 상태 입력이며, EV 감속기 기구와 같은 것이 아니다. EV가 곧 HPC 중앙화 아키텍처라는 뜻도 아니다.

## 재사용과 변경 파일

기존 C/WASM+Rapier·단일 차량 기록·독립 19시나리오·typed 연결 엔진·원래 모모·밝은 UI·뒤로가기/백업을 유지했다. 팀원 조립 기반의 부품 모델을 그룹 단위 진행으로 확장했다. 원본 TRACKBACK/팀원 프로젝트는 수정하지 않았다. 보관한 데이터는 여전히 검수되지 않은 원본을 정답으로 사용하지 않는다.

- `domains.ts`, `AssemblyKits.tsx`, `KitFlow.tsx`, `ArchitectureBoard.tsx`: 도메인 묶음/입출력/스케치/실제 장착 누적.
- `LearningStudio.tsx`, `Puzzle.tsx`, `DriveLearning.tsx`, `MomoCampaign.tsx`, `journey.css`: 설계·실행 분리/작은 조건 퍼즐/관찰 UX/다음 행동.
- `CarBody.tsx`, `Scenery.tsx`, `MarketIntro.tsx`, `CinemaIntro.tsx`: 새 외형·접지·구매·영화·도로 사건.
- `CockpitPaws.tsx`, `DriveExperience.tsx`, `CatDriver.tsx`, `WorkshopScene.tsx`, `Hardware.tsx`: 입력 연동 손발/눈/시점/그림자/현가 표현.
- 테스트: 실제 6묶음→15종 기록/6하네스, 도로 사건, 조작 중복 없음, 작은 조건 퍼즐/탭 흐름, 손-핸들/기어 애니메이션 회귀 추가.

## 명시적 미완료와 다음 완결 단위

현재 전체 차량의 모든 부품/도메인을 설계·검증하는 프로그램은 아니다. 충전·BMS·열관리·ADAS·차체·현가 제어 SW는 지도에서 참고/후속 범위다. 현가 코일은 제공 섀시의 형상 표현이며 압축량 해석을 새로 구현한 것은 아니다. 직접 제동·조향 SW 제작, 내연기관 해체→EV 이식도 후속이다.

차량은 원본 곡면 스타일 모델이고, 손은 입력에 맞춰 움직이는 절차적 리그다. 완전한 양손 IK/손가락 접촉/탑승 애니메이션, 실제 파손 물리, 고품질 시장 NPC/서류 소품 연출, 실제 영화 영상은 구현하지 않았다. Nintendo/OEM 납품 수준이나 교육 효과 검증 완료를 주장하지 않는다.

검사 수치와 실제 화면 QA는 `qa-v14/RESULTS.md`에 기록한다. 다음은 기능을 더 얹기보다 신규 사용자 3~5명이 이 흐름을 도움 없이 한 사이클 진행하는지 평가하고, 막힌 위치를 기준으로 안내와 전환을 보정하는 것이 우선이다. 후속 요청은 `FOLLOW_UPS.md` 상단을 따른다.
